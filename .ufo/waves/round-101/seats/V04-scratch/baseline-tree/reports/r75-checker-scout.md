# Round 75 checker scout — repeated relation rows

## Scope and disposition

This report supports only the Round 75 **coverage** hypothesis: exact duplicate relation rows may be an unvalidated input condition. The concurrent Round 75 depth declaration about a fictional registry entry was withdrawn and unexecuted; it is incident telemetry, not this report's scope or evidence. Scout only. No checker or fixture edits were made; the only repository file written by this scout is this report. **GO** for the narrow factual claim that the current checker does not detect an exact repeated relation tuple, and that a repeated-row probe is a distinct structural input condition. **NO-GO for treating repetition itself as a harmful or semantically invalid assertion on present evidence.** The schema and documentation do not establish whether two identical rows represent accidental duplication or repeated mentions. This scout does not approve implementation or claim coverage gain is materially useful.

## Validation path and old behavior

- `corpus/fixtures/check_bible.py:25-32` declares the `relations` row fields as `from`, `to`, `type`, and `source_id`, all strings. The loader at `:41-76` admits each schema-valid array row in order and keeps its `relations[index]` location. It does not compare relation rows against each other.
- Relation validation at `check_bible.py:161-169` iterates each admitted relation independently. If entity data is available it checks both endpoints for dangling or ambiguous IDs (`:162-168`), then checks that row's `source_id` (`:169`). There is no relation identity/count index in this path.
- The special alliance path at `:249-267` filters `allied_with` rows and checks whether each eligible distinct faction edge has a reverse `allied_with` edge with a unique source citation. This asks about reversed endpoints, not identical tuple repeats; a duplicate forward row cannot supply the reverse edge.
- To reproduce old behavior without changing the corpus, I made a temporary copy of `fixtures/consistent/` outside the repository and appended a byte-equivalent copy of its existing `mira -> seal`, `carries`, `courier-log` row to `relations.json`. Running `python3 .shokunin/lore/corpus/fixtures/check_bible.py <temporary-copy>` exited **0** and printed `CLEAN: schema, citations, relations, timeline; 0 violations`. This confirms exact repeated rows are accepted by the current CLI. It is a local probe, not a new committed fixture or policy test.
- The control source is `fixtures/consistent/relations.json:1-8`, which contains that single row. The baseline claim in `.shokunin/lore/LOG.md:1363-1365` likewise says the 132 shipped fixtures had no exact repeated relation tuple and flags the meaning of repetition as open. I did not independently replay all 132 fixtures in this scout.

## Fixture README and relevant precedents

- `fixtures/README.md:12-27` documents the round-2 `allied_with` reciprocal convention: only distinct existing faction pairs, same relation type and reverse direction; other relation types and self-edges are outside that rule. It explicitly says this is a chosen data convention, not proof every alliance is symmetric. It does not define duplicate-row semantics.
- Round 2's scout, `reports/r2-rule-scout.md`, directly notes that the checker did not validate duplicate relations; it warns that two identical A-to-B alliance rows do not provide a reverse edge, and says duplicate-relation policy was undeclared and should not be added as a symmetry failure. This is the closest prior relation-specific statement, though made in the context of alliance reciprocity rather than a generic duplicate diagnostic.
- The README's round-8 section (`fixtures/README.md:150-168`) describes repeated `depends_on` entries as an input-list duplicate accepted by the old checker, then reports repeated occurrences locally without interpreting causal truth. This is precedent that one schema collection has an explicit repeated-member policy; it does not itself establish the same policy for relation rows.
- The relation-ID ambiguity precedents distinguish row duplication from duplicate endpoint IDs. `fixtures/README.md:514-533` and `:538-552` say endpoint IDs matching multiple entity rows produce local ambiguity plus a global duplicate-entity finding, while retaining the relation and not selecting an entity row. `reports/r7-alliance-scout.md` concerns duplicate *source IDs* and qualification of an alliance witness, not duplicate relation tuples. Neither is evidence that relation repetition itself is invalid.
- `reports/r37-duplicate-scout.md` covers duplicate timeline event IDs and ledger endpoint resolution; `reports/r59-parser-scout.md` and README `:938-946` cover duplicate JSON object member names. These are materially different duplication layers and should not be presented as precedent establishing relation-row deduplication.

## Structural boundary and limitations

An exact duplicate under the LOG hypothesis is the same ordered tuple `(from, to, type, source_id)` repeated in one `relations.json` array. That is distinct from a reverse edge, a repeated source ID, duplicate entity IDs at endpoints, a duplicate JSON object key, or two different relation rows with distinct citations. The proposed check is structural only. Even a diagnostic at the later `relations[i]` row would show only that its fields repeat an earlier input row; it cannot establish that the same assertion was authored twice by mistake, that only one report exists, or that the relation is uniquely true.

The current schema has no relation-row identifier, occurrence/mention field, or multiplicity contract (`check_bible.py:25-32`). A single `source_id` is just checked against the in-world source table (`:97-109`, `:169`); it does not cause the checker to inspect source prose or verify support. Thus two equal rows with one cited source could be a redundant copy, or could be intended as separate mentions that this schema cannot distinguish. A duplicate detector could flag a structural repeat without making that semantic distinction, but calling it an error or violation risks implying a stronger contract than observed.

**Not established:** source-text truth or authenticity; canonical status or uniqueness of a fictional relation; whether duplicate rows represent multiple mentions; rights, ownership, or permissions; gameplay/mechanics; completeness of any relation list. No external source is consulted. Structural cleanliness is not a truth judgment, and structural duplication is not proof of a false relation.

## Conclusion

The proposed relation-row duplicate test would cover a branch absent from current relation validation in the narrow sense of detecting exact input repetition. But the current schema/documentation leave the intended multiplicity unresolved, and r2 already cautions against smuggling a duplicate policy into relation reciprocity. **GO** to continue investigating a clearly labeled input-level diagnostic with matched controls; **NO-GO** to conclude from this scout alone that repeated identical rows are semantically harmful, canon-invalid, or warrant a hard violation. Any future candidate should preserve distinct-source and reverse-edge rows, state explicitly whether it is warning or violation, and keep its claim limited to row structure.
