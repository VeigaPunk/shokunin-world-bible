# Round 44 precedent scout — actor ontology and prior coverage

**Scope:** read-only precedent audit; no checker, fixture, README, or LOG edits. The requested output is this report only.

## Finding: character-only actor premise is not established

The proposed premise must be rejected as an ontology rule. The schema calls the timeline member `entity_id`, not `character_id` (`.shokunin/lore/corpus/fixtures/check_bible.py:12`). The active checker resolves membership and ambiguity for this field, then uses its ID for occupancy, without reading the actor entity’s `kind` (`check_bible.py:230-236,245-252`). By contrast, it explicitly validates the `place_id` kind (`check_bible.py:237-241`). README wording that “A character cannot occupy different places at the same tick” is a bounded occupancy statement, not a declaration that only characters can be timeline subjects (`.shokunin/lore/corpus/fixtures/README.md:29-34`). The same README describes `entity_id`-style holders as entity IDs whose kind need not mean legal ownership (`README.md: the Round 6 item-chain section, search “Holder IDs are entity IDs”; lines 87-90 in current file). No automatic character-only convention follows from those statements.

Inventory provides no counterexample to that reading, but is not proof of a restriction: scanning the 95 fixture directories/228 timeline rows found only uniquely resolved `character` actors plus missing `unlisted` IDs in `r13-missing-actor`; none assigns a unique place/faction/item as `entity_id`. Active fixtures therefore do not demonstrate that non-character actors are valid in-world, but neither establish they are forbidden. A new rejection diagnostic for a unique non-character actor would impose a new ontology constraint absent from the schema and documented rule.

## What prior rounds do and do not cover

- **Round 11 is not precedent for actor-kind validation.** The exact checked-in fixture pair has one character and one place sharing `harbor`; the timeline references `harbor` in its `place_id`, not `entity_id` (`fixtures/r11-character-place/entities.json:10-27`; `fixtures/r11-character-place/timeline.json:2-10`; pair inversion is `fixtures/r11-place-character/entities.json:10-27`). Round 11’s declared change is explicitly scoped to `timeline[i].place_id`; duplicate place IDs trigger ambiguous-place handling, while unique non-place `place_id` stays “not a place” (`LOG.md: round 11 post-scout clarification and closure`; `reports/r11-fixture-scout.md:9-13,36-42`). This tests last-row kind selection for a location slot, not actor semantics. The r11 unique-nonplace fixture likewise alters `place_id` to `mira`, not actor ID (`fixtures/r11-unique-nonplace/timeline.json:2-10`; `reports/r11-fixture-scout.md:13,30-41`).
- **Round 12 covers ambiguous identity, not kind.** Its paired timeline records use `entity_id: "mira"`, a character in both fixtures; ambiguous case adds a second schema-valid `mira` character row (`fixtures/r12-ambiguous-actor/entities.json:1-17,36-47`; `fixtures/r12-ambiguous-actor/timeline.json:2-20`; unique control `fixtures/r12-unique-actor/entities.json:1-17`, timeline same shape). The declared/implemented rule suppresses definite occupancy attribution for a multiply-resolved actor ID and reports ambiguity (`LOG.md: Round 12 post-scout clarification and closure`; `reports/r12-fixture-scout.md:11-37`). It offers no evidence for rejecting a uniquely resolved place/faction/item actor.
- **Round 21 covers malformed dependencies masking occupancy, not actor kind.** Its unique-actor control and malformed dependency pair both use `mira`; the sole intended change is `depends_on: []` versus `[null]` (`fixtures/r21-clean/timeline.json:2-20`; `fixtures/r21-malformed/timeline.json:2-20`; `reports/r21-fixture-scout.md:1-26`). The accepted change moves independently certain occupancy evaluation ahead of malformed dependency handling (`LOG.md: Round 21 post-scout clarification/closure`). It assumes the same actor identity and makes no claim about the set of permitted entity kinds.

These precedents do establish narrower rules: place slots must refer to places; ambiguous actor identity cannot support a definite actor-level occupancy comparison; malformed dependency content must not mask otherwise eligible occupancy. None licenses an unconditional character-kind rule on generic `entity_id`.

## Risks and recommendation

**No-go** on the proposed `entity_id: not a character` diagnostic or any restriction of timeline actors to characters absent a separately declared, source-backed ontology convention. The fact that a unique place actor can pass current validation is not itself a defect: checker validity does not assert a narrative event is true, and its generic field/schema permits any uniquely identified entity structurally. Rejecting it would harm calibration by turning an unstated convention into a violation. README’s character occupancy sentence is not sufficient: it states a character rule, not the converse “only characters may be actors.”

If the round’s intended question is strictly whether a place-as-actor *in a character-location event* should be screened, that needs a narrower premise grounded in a field/event-type contract that current schema does not encode. Do not implement based only on a proposed fixture whose `description` calls it a character-location event; description is free text, not a typed event class. Existing checks should remain unchanged pending such a contract.

## Falsifiable go/no-go

- **NO-GO (current evidence):** do not implement an actor-kind restriction. Falsifiable basis: checker schema is generic `entity_id`; README provides no “only characters” rule; r11/r12/r21 precedents do not test unique non-character actors. A future go requires a documented, explicit timeline actor-kind contract (or typed event category with allowed actor kinds) independent of the synthetic example, plus paired character/non-character controls and proof old fixtures remain unchanged.
- **GO only for a different, justified move:** if future evidence establishes such a contract, a minimal test must show the uniquely resolved character control remains clean and the otherwise identical uniquely resolved disallowed-kind actor receives a local diagnostic; this must be tested for each allowed/disallowed kind and no unsupported broader inference. Reversal condition: if a valid in-scope event is shown whose actor is a place/faction/item, an unconditional character-only guard is falsified and must not ship.

No implementation or fixture mutation recommended for r44 on this premise.
