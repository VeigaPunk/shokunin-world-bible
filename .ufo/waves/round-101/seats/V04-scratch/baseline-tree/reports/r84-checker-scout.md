## Exact validation, index, and count flow

1. The timeline schema requires `id: str`, `tick: int`, `entity_id: str`, `place_id: str`, `depends_on: list`, `description: str`, and `source_id: str` (`check_bible.py:25-32`). Each section is JSON-loaded; a row is appended to `data[section]` only when it is an object and every required field has the declared exact type and, for strings, nonblank content (`:41-76`). Thus “duplicate IDs counted” below means repeated IDs among timeline rows that passed this required-field screen. Timeline referential problems are not this schema screen.
2. `index(section)` iterates those admitted rows, reports `timeline[n].id: duplicate timeline id ...` on a repeated key, then still assigns `result[row['id']] = row` (`:78-84`). Consequently `events = index('timeline')` is a last-valid-row-wins mapping (`:86-92`); a duplicate diagnostic does not remove either row from `data['timeline']`.
3. Separately, `event_id_counts` increments once for every admitted timeline row (`:93-95`). The contradiction-ledger endpoint consumer checks that the referenced ID count is exactly one and continues without dereferencing an ambiguous endpoint otherwise (`:113-141`, particularly `:127-135`). Dependency validation also consults counts: zero is unknown, >1 is ambiguous, and only a unique dependency proceeds to tick lookup (`:295-316`). These are distinct event-ID consumers.
4. Occupancy then loops directly over **all** admitted `data['timeline']` rows (`:269-270`); it does not consult `events`, `event_id_counts`, or event IDs. For each row it independently checks actor and place entity-ID counts (`:271-284`): duplicate actor IDs are diagnosed, a place with duplicate IDs is diagnosed, a uniquely resolved non-place is diagnosed, and `comparable_place` is true only for one entity row of kind `place`. It calls `source(...)` at `:285`, but does not use the returned source status in occupancy. Negative ticks get a local diagnostic at `:286-287`.
5. The occupancy admission predicate is precisely: entities available, exactly one actor entity row, `comparable_place` true, and nonnegative tick (`:288`). Its key is `(row['entity_id'], row['tick'])` (`:289`). If that slot is already stored with a different raw place-ID string, it emits `double-booked` using the current row and the stored first row's location/place (`:290-292`). Otherwise (including same-place repeats) it stores `(location, row['place_id'])` (`:293-294`). There is no event-ID uniqueness condition in either branch.

Therefore, if two schema-admitted timeline rows have duplicate event IDs but each independently meets the occupancy predicate and has the same uniquely resolved actor/tick and a different uniquely typed place, the current code reaches the same `double-booked` branch as it would for distinct event IDs. The duplicate ID finding is produced separately by `index('timeline')`. The source call also runs separately and does not gate occupancy. This establishes the flow, not whether a raw-row conflict remains actionable despite ambiguous event labels.

## Assessment boundary

A duplicate event ID makes an ID-keyed event referent ambiguous for consumers that need one event (as the ledger/dependency paths explicitly handle). Occupancy instead compares the supplied row fields directly, keyed by actor and tick, retaining the first qualifying row's raw place reference. It is plausible either that these two row assertions independently provide enough structural input for a location collision, or that ambiguous event identity makes the definite message overstate what can be concluded. This inspection does not choose between those interpretations and does not assume a bug. A matched duplicate-ID/distinct-ID CLI probe, exact outputs, and editor-action evidence would be needed to assess calibration. No story truth, canon, rights, or mechanics conclusion follows from these checker paths or citations; authored fixture prose remains fictional/unverified, and local ticks are not actual dates.
