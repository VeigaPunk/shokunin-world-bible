# Round 78 prior-art scout — copied ledger-side source metadata

## Disposition

**NO-GO on implementation/admission from prior art alone; conditional GO only for the proposed matched materiality probe.** The exact mismatching extra `source_id` value is not shown as an executed prior fixture, so that concrete input may be new. But permissive extra members, the ledger’s documented citation convention, and the absence of demonstrated reader confusion make a new checker rule or calibration gain unproved. A novel value in an already documented structural convention is not by itself a material move.

## Active convention and implementation

The active `check_bible.py` requires each contradiction side to be a dict with usable `event_id` and allowed `field` (`place_id`, `tick`, `depends_on`). It resolves exactly one timeline event, then obtains citation status from that event row’s `source_id`. The side’s `source_id` member is not read or checked. General row/side validation checks required fields, not a closed-object key set, so unknown keys are accepted. This behavior is permissive, not an explicit promise that every extra member is meaningful or safe.

README Round 3 makes the strongest convention explicit: each side is “of the form `{ "event_id": "...", "field": "..." }`”; allowed fields are named; “The event's own source is the citation for that assertion; the ledger does not copy a source, text, or paraphrase that could disagree with it.” The checker checks pointers and source-ID resolution, **not** citation truth or support. This is a documented single-citation-source convention, though there is no explicit statement that all extra keys are forbidden or that arbitrary extension metadata is rejected. A copied side source that conflicts with the target event would be outside the documented citation representation and ignored by current code; its presence does not establish that readers actually treat it as authoritative.

## Novelty and materiality boundary

I found no retained report among these requested precedents that executes the exact matched unique-event pair with side `source_id` equal to versus different from the event’s `source_id`. Treat that narrow test as **not located in retained evidence**, not proof no transient probe ever existed. Crucially, baseline checker behavior for both values is identical because it ignores the extra member; no existing finding is replaced or falsified. Whether a human editor would read the stray value as a citation is an open usability question. README’s explicit “does not copy a source” rule cuts against treating it as a supported second citation authority, while the JSON shape is not closed and the checker does not flag the deviation. Material calibration therefore requires independent reviewers to show that the mismatch changes a concrete attribution/repair decision, not merely that the field is ignored or undocumented.

If the matched probe proceeds, hold all else constant: uniquely resolving target event and source; side field absent, matching source, then conflicting source; plus malformed/unresolved event controls. Capture full diagnostics and ask a non-author reviewer what citation they would use and what repair differs. A new rule should be confined to a contradictory copied citation; do not silently ban unrelated extension fields or make side metadata a second source of truth. If the checker diagnoses the mismatch but no reader’s attribution or repair changes, or reviewers regard it as inert undocumented metadata, the materiality claim is falsified. Any implementation would also need preserve old 132 raw fixture tuples as the active round declaration requires.

## Limits

This is a code/schema/documentation and retained-report audit, not evidence about any fictional excerpt, source authenticity, what a source supports, canon, chronology, rights, or mechanics. “Unique” or “resolvable” means only identifier status in the supplied fixture. No checker, fixture, README, or LOG change is recommended by this prior-art report.
