# Round 62 critic — affected-event repair hints and independent findings

## Independent verdict

**NO-GO on material new calibration on the present evidence.** The proposed timeline-index availability distinction is technically coherent, but the declaration itself identifies two unresolved materiality risks: it withholds useful ledger-side event-ID repair pointers, and r7/r39 may already have exercised the same ledger pointer behavior. I would not authorize implementation/admission without an actual matched replay showing that the lost lines are misleading rather than useful and that independent ledger checks survive. This is a critic assessment, not a claim that a candidate was implemented or replayed.

## Observed checker behavior

In `.shokunin/lore/corpus/fixtures/check_bible.py` (current lines 22–43), every table begins `loaded=True`; read/parse/duplicate-member errors set `rows=[]` and `loaded=False`, while non-array input is also replaced by `[]` and sets `loaded=False`. Only `entities` and `sources` currently retain availability flags (lines 35–43). Timeline is therefore represented as an empty admitted row list for both unavailable and successfully loaded-empty inputs.

At lines 77–80, the checker builds the event index and counts IDs from admitted timeline rows. Contradiction sides are validated independently for event_id and allowed field at lines 82–94; then `event_id_counts.get(event_id, 0) != 1` emits `contradictions[…].claim_*.event_id: expected exactly one timeline event …` and continues (lines 94–97). Thus an unavailable timeline currently produces the same zero-match ledger diagnostic as a successfully loaded empty timeline. The ledger loop's malformed side/object, event-id type/blank, allowed-field, and distinct-claim checks do not require event membership (lines 82–115). Entity/source diagnostics and relation/timeline rows that did load are separate passes; failed timeline rows cannot supply row-local checks, but do not justify suppressing independent diagnostics from other files.

Timeline dependency checks at lines 294–320 operate on retained timeline rows. An unavailable timeline supplies no parsed dependent rows, so there is no evidence-based dependency cascade to “repair”; do not invent dependency diagnostics for rows that failed to load. By contrast, loaded rows' `depends_on` type, self/repeated reference, unknown/ambiguous event, and tick-order checks are part of the existing contract and must remain unchanged.

## Novelty / prior-art challenge

R7 reports and r39 evidence concern contradiction-ledger event pointers/cardinality and must be searched at the exact case level, not inferred from the r60/r61 availability analogy. R39 specifically established that a *loaded* uniquely resolved event can produce a ledger-side no-resolvable-source result, and a timeline-local unknown-source result; it did not, on the evidence inspected, establish unavailable timeline behavior. R7's duplicate/ambiguous source and ledger work similarly demonstrates ledger-local findings, not by itself unavailable timeline. The r60/r61 admitted changes are availability of different target tables; they do not confer novelty on timeline or prove its hint-loss acceptable. If historical exact probes or reports already show the unavailable-timeline/empty-ledger equivalence, the move is not a new calibration discovery; at most it is a durable test of a known policy, whose value must be defended separately.

## Benefit versus cost

Potential benefit: do not label an event ID as absent from the supplied timeline when the index failed to load. Keep the direct `timeline.json` parse/shape diagnostic and withhold only event-index membership/cardinality conclusions that require the unavailable full index. Loaded `[]` remains available and must still produce the current expected-exactly-one finding. A loaded partial array remains an available supplied index; absence within it continues to be reported under existing semantics.

Cost: the ledger diagnostic is an affected-reference hint. Suppressing it tells the maintainer which contradiction rows reference each affected event ID. The single file-level load error does not identify those references. This cost is concrete even though the membership conclusion is unsupported. A material calibration gain therefore requires either (a) retain affected locations explicitly as “not assessable: timeline unavailable” (clearly distinct from missing), or (b) show by paired probes that omitting them is still materially clearer/actionable and not a net loss. Merely replacing one specific line with a generic file error risks lower repairability. If retaining scoped hints is feasible, prefer it over silent withholding, but do not let the status phrase imply the event exists.

## Falsifiable probe and acceptance conditions

Use identical copies outside the repository, holding `sources.json`, `entities.json`, `relations.json`, and `contradictions.json` byte-identical. Vary only `timeline.json`: missing; malformed JSON; duplicate-member JSON; nonarray; successfully loaded `[]`; loaded partial with relevant IDs absent; loaded rows with duplicate relevant event IDs; and a matched loaded control containing the relevant unique events. Include contradiction sides with valid unique event IDs, unknown event IDs, malformed/blank IDs, invalid fields, and equal claim references. Add independent malformed entity/source/relation inputs in a separate paired control to verify those diagnostics still print when timeline is unavailable. Capture complete stdout/stderr/exit and byte hashes.

Observed current behavior is not a proposed output: failed timeline currently emits load/shape error plus ledger “expected exactly one timeline event” findings; loaded empty emits the ledger findings without a load error. Proposed candidate should retain the file error; withhold or explicitly mark unassessable only ledger event-ID lookup/cardinality; retain local ledger shape/type/field/distinctness and every unrelated table finding; preserve current loaded-empty/partial/duplicate behavior. Falsifiers: any independent ledger or other-table diagnostic disappears; unavailable is called empty/absent/clean; loaded empty stops reporting; duplicate loaded IDs stop being ambiguous; or affected-event pointers vanish without an explicit, materiality-justified repair policy. Do not fabricate event/dependency findings for rows absent from an unavailable file.

For a material admission, independently replay the pinned baseline's entire corpus path/byte inventory and all old raw `(exit, stdout, stderr)` tuples, then enumerate every candidate delta. No code/fixture changes are authorized by this report. The declared scope permits only a timeline-specific availability policy; it does not justify a generic loader refactor.

## Epistemic boundary

This is only about membership/cardinality in supplied JSON input. A loaded-table missing ID is not proof of actual or fictional-world absence; an unavailable table supports no membership conclusion. Neither event ID, tick, dependency, nor ledger pointer establishes that an event occurred, source prose supports it, chronology, truth, canon, rights, license, or permission.
