# Round 78 schema scout — ledger-side `source_id` metadata

## Disposition

**NO-GO for a hard error solely because a contradiction-ledger side has an extra `source_id`, including a value that disagrees with the referenced event.** Current project documentation specifies the side pointer shape as `{ "event_id": "...", "field": "..." }` and expressly says the event's own source is the citation; it does not define ledger-side `source_id` as a second citation. But the active checker does not enforce closed objects generally, and no producer contract says extra side members are forbidden. Thus it may be inert extension metadata under current implementation, not a schema violation. A copied key named `source_id` can nevertheless mislead a human reader into treating it as an authoritative citation. The evidence supports a documentation/interpretation caution, not a new hard-error rule on this inspection alone.

## Evidence and contract boundary

- `corpus/fixtures/README.md`, Round 3, documents every ledger side as `{ "event_id": "...", "field": "..." }`, says the event's own source is the citation, and says the ledger does not copy a source, text, or paraphrase that could disagree. It describes pointer/text validation, not a strict prohibition on unlisted metadata keys.
- In `corpus/fixtures/check_bible.py`, the top-level contradiction row's required fields are `id`, `claim_a`, `claim_b`, and `why`. A side must be a dict; the checker reads `event_id` and `field` with `.get()`, then resolves the event and checks **that event row's** `source_id` through `source_status`. No side `source_id` is read, compared, or validated. Extra members on side dicts (and most other ordinary records) are tolerated. Consequently an extra side `source_id`, matching or conflicting, currently has no checker effect; it neither replaces nor supplements the event citation in machine behavior.
- Distinguish the declared *pointer shape* from a closed JSON Schema: README gives two expected pointer members, but neither its wording nor current generic row validation establishes rejection of all additional members. R3's schema scout likewise observed permissive general loading and recommended against generic optional-file changes; r3 adjudication confirms the chosen ledger's scope was structural pointer/citation-ID resolution, not semantic verification. R63's prior report notes the broader checker behavior that unknown extra members can be ignored; that is relevant compatibility precedent, not proof that every metadata key is desirable.
- No inspected README/report establishes a supported producer or consumer contract for ledger-side extension members, whether such metadata is intentionally used downstream, or that every extra `source_id` is meant to assert a citation. Compatibility is therefore unresolved, not evidence that the member is formally sanctioned or formally forbidden.

## Risk and recommendation

A side-level key literally named `source_id` creates plausible reader confusion: a reviewer may mistake it for a second or overriding citation even though the checker ignores it and README assigns citation authority to the event. If its value conflicts with the event, the mismatch could be especially misleading. Conversely, a hard error for this member changes the currently permissive object contract, can reject otherwise usable ledgers with extension metadata, and would codify a closed-schema exception not currently stated for these sides. A test proving that the checker ignores it demonstrates behavior, not that rejection is the correct compatibility policy.

Prefer explicit documentation that only the event's `source_id` is citation-bearing and that side extras are not validated/authoritative, or establish a closed side-object contract with producer/consumer compatibility evidence before rejecting extras. If a future narrowly scoped rule is considered, it should target only the disputed member and be justified by matched equal/conflicting controls and actual repair impact; it should not imply validation or prohibition of arbitrary extra metadata. Do not classify metadata as an alternate witness or let it affect citation resolution absent an explicit schema decision.

## Limits

This is a code/documentation compatibility assessment, not an independent runtime probe of matched side values. It makes no source-text support, source authenticity, event-truth, chronology, canon, rights, or mechanics inference. It does not recommend changing the checker, fixtures, or README in this round.
