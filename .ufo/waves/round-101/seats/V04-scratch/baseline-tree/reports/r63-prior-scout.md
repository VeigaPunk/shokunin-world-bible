# Round 63 prior-scout — non-finite JSON token precedent and producer contract

## Disposition

**Conditional GO for a narrowly scoped material calibration probe; NO-GO for implementation based on this audit alone.** Current checker behavior creates a concrete, distinct malformed-input case: Python's permissive decoder accepts `NaN`, `Infinity`, and `-Infinity`, although these spellings are not JSON number values under the JSON interchange format commonly specified by RFC 8259. An unknown member containing such a token can be discarded by the checker’s field allowlist and produce CLEAN. This differs from r5's invalid-syntax probe and r59's duplicate-member policy. However, I found no explicit producer contract, strict-JSON statement, or supported-producer compatibility evidence in the fixture README/knowledge materials. Novelty is plausible, but material calibration and the local producer assumptions remain to be verified independently.

## Evidence: current path and actual behavior

- `corpus/fixtures/check_bible.py:45-53` calls `json.loads(..., object_pairs_hook=unique_object)` and catches `JSONDecodeError`, duplicate-member error, and I/O/Unicode errors. It does not override Python's `parse_constant`; Python therefore admits the nonstandard constants as floats. At `:65-76`, only declared required fields are validated and valid rows are retained; unknown extra keys are not rejected. Thus a non-finite value in an ignored extra member can disappear from the checker’s semantic view.
- I independently copied `consistent/` to a temporary directory outside the repository, added `"extra": NaN` to `sources[0]`, and ran the active checker. **Observed:** exit 0 and `CLEAN: schema, citations, relations, timeline; 0 violations`. This confirms the reported case, not a story fact. No repository fixture or shared code was changed.
- A quick later scratch probe was malformed by my string splice and yielded ordinary `JSONDecodeError`; it is not evidence about Infinity. Do not cite it as a valid probe. Exact paired Infinity/-Infinity tests should be done with a JSON-aware text construction and independently replayed.

## Prior art and boundary

- **R5** (`reports/r5-loader-scout.md`; `corpus/knowledge/2026-10-12-malformed-error-patterns.md`; README “Round 5”) tested missing file, `{` syntax error, `{}` wrong top-level shape, `[7]` row shape, and unknown citation. The `{` case is malformed standard JSON and shares the generic loader-error category, but no r5 input tested Python's accepted non-finite constants. R5 explicitly limits its matrix and claims no exhaustive malformed-input coverage. It establishes loader-error precedent, not this token behavior or its materiality.
- **R59** (`reports/r59-prior-scout.md`; LOG “Round 59 — closure”) adopted `object_pairs_hook=unique_object` to reject repeated object member names at any depth instead of Python's last-wins behavior. That hook addresses duplicate names only; it does not validate number constants. The precedent supports a parser-boundary policy and file-level rejection, but does not make non-finite rejection an already implemented rule. R59 found no supported producer last-wins contract; that is not proof there is no producer contract for Python constants.
- README describes required JSON tables and structural validation, but I found no explicit RFC/strict-decoder requirement or producer identity/version. The standard-format premise is technically strong but should be stated as an input-format convention, not an observed local producer guarantee. No format or producer evidence currently falsifies the candidate; compatibility is unresolved, not established.

## Probe needed before admission

Use matched copies of the same clean five-table bytes. Inject each constant (`NaN`, `Infinity`, `-Infinity`) into (a) an ignored extra member (current clean bypass), (b) a required typed field such as `timeline.tick`, and (c) a nested object/array value such as an entity claim or ledger object. Compare with unique-key, valid finite-number controls and with existing malformed JSON r5 control. Capture complete stdout/stderr/exit and exact input hashes. Test the active checker and a narrowly strict parser candidate; also check how rejecting the whole file affects source/entity/timeline availability gates and dependent findings. A robust change would preserve the primary file/token error, avoid claiming that ignored unknown fields are semantically validated, retain independent checks, and not mistake unavailable for empty. If it only adds another generic syntax case without a consequential observed false CLEAN/decision, or if supported producers rely on these values, calibration gain is not established.

## Falsifier, harm, and rights/canon boundary

Falsify the candidate if a supported producer/input contract intentionally emits Python's constants and defines their meaning, or if paired replay shows no material checker misclassification and strict rejection introduces disproportionate cascades/noise. Prospective harm: a file-level rejection can unload a whole required table, producing dependent lookup diagnostics or triggering existing availability handling; this is more costly than a field-local error and must be measured. The observed `NaN` in an ignored metadata key demonstrates input acceptance only. Rejecting it would establish format validity under a chosen JSON contract—not source-text support, fictional truth, event chronology, canon, ownership, rights, licensing, or permission. Preserve raw inputs; do not reinterpret a token as a lore assertion.
