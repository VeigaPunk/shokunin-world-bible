# Round 42 prior-art scout: unsupported ledger field

## Decision

**No-go on the proposed calibration candidate as a genuinely distinct move.** The planned `claim_a.field: description` probe is a new concrete value/fixture only if implemented, but it repeats an already executed unsupported-field case in round 3. Round 3's non-author reviewer explicitly says temporary copies tested an “unsupported field,” exited 1 with a diagnostic, and did not crash (`.shokunin/lore/reports/r3-reviewer.md:7`); the verifier separately tested malformed pointers but does not claim unsupported-field coverage (`.shokunin/lore/reports/r3-independent-verifier.md:1-4`). The r3 reviewer locates the allowed-field boundary and notes extra keys in reference objects as permissive (`r3-reviewer.md:9-10`). Hence `description` versus some other invalid token is not fresh calibration evidence absent a distinct semantic question and an independent criterion.

## Evidence and boundary

- Round 3 made ledger entries event-field references and deliberately allowed only `place_id`, `tick`, `depends_on` (`.shokunin/lore/LOG.md:33-35`). The current checker enforces the allowlist at `.shokunin/lore/corpus/fixtures/check_bible.py:76-90`; its diagnostic is structural membership, not interpretation of event text.
- The round-3 fixtures/README says allowed fields are those three and that the checker validates pointers/required text, **not** whether `why` explains a semantic contradiction (`.shokunin/lore/corpus/fixtures/README.md:17-24`). The corpus README records the original r3 run evidence and fixtures (`.shokunin/lore/corpus/README.md:5-9`).
- The r3 reviewer’s executed temp probe directly subsumes “unsupported field rejected” (`r3-reviewer.md:7`). Its final conclusion explicitly bounds success to structural pointers/citations, not semantic truth or entailment (`r3-reviewer.md:9-13`). The r3 adjudicator also judged calibration unchanged, since no prior calibration measurement existed (`r3-axis-adjudicator.md:5-12`).
- R42 declaration itself acknowledges r3 temporarily tested an unsupported ledger field and says this round must avoid claiming a new checker branch (`.shokunin/lore/LOG.md:624-626`); its proposed `description` selector rationale distinguishes event prose from assertion selectors, but no evidence shows that distinction was absent from r3's stated structural-versus-semantic limits.

## Risk

Calling this calibration improvement would inflate coverage of an already tested allowlist failure into semantic calibration without a demonstrated new decision boundary. `description` is indeed an event field in the data model, while it is not a ledger selector; however, the checker cannot determine whether free prose supports or contradicts a claim, and round 3 already documents that limitation. A fixture showing the same expected allowlist error cannot establish how a human should read the prose, let alone validate `why`. Do not infer that descriptions are never useful, that an event description is false/forbidden, or that the two Bell-7 reports/canon are resolved.

## Falsifiable check / reconsideration gate

Before any executor work, inspect the full archived `reports/r3-reviewer.md` and temporary unsupported-field command/output (the report does not preserve the exact token, mutation, or raw transcript). If that artifact establishes only a generic malformed-field rejection and does **not** test or state the distinction “event prose is not an assertion selector; human prose interpretation is not checker proof,” then a candidate could be reconsidered only with a pre-registered, independently reviewable semantic decision test: same r35 control/ledger prose, one selector changed to `description`; expected structural allowlist rejection, plus an explicit human decision table that refuses to infer semantic conflict from the prose or checker diagnostic. It would count only if a non-author reviewer can identify a materially new, observable calibration decision that r3 did not already settle. If the reviewer reaches the same bounded conclusion as r3, or the only delta is the spelling of the invalid selector, record **no-go**. This check is falsifiable and requires no canon inference.
