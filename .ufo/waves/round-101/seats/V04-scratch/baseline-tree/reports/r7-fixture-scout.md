## Proposed paired fictional-source fixtures (not implemented)

Use small sibling directories copied from existing clean fixtures, preserving fictional entities and all unrelated tables:

1. **Alliance unique-source control:** base on `ally-reciprocal`; exactly one `harbor-compact` source row, both directions cite it; expected clean as existing control.
2. **Alliance duplicate reverse citation:** retain two reciprocal rows, but duplicate `harbor-compact` in `sources.json`; make only the reverse edge cite that ambiguous ID, and cite the forward edge to a separate unique fictional source. Preserve the duplicate source rows. Expected: duplicate-ID diagnostic plus a local indication that the unique forward relation has no uniquely sourced reciprocal. Do not select either duplicate record. This is stronger than the existing both-directions-same-duplicate shape because it isolates qualification of the reverse witness.
3. **Item unique-source control:** existing `item-chain-valid` is a usable positive fixture with all provenance citations uniquely resolved.
4. **Item duplicate-citation sibling:** copy `item-chain-valid` and duplicate one source ID actually used by a provenance record, keeping the record and both source rows intact. Expected: duplicate-ID diagnostic and a local ambiguous citation / explicitly unqualified provenance record, not an `unknown source` claim. Separately use the existing `item-chain-broken` relation mismatch (or its sibling with only a duplicate source) to state whether predecessor mismatch is a structural assertion check or is meant to require qualified citations. Avoid implying an ambiguous citation proves the reported history.

For both domains, add an **unrelated-duplicate negative control**: duplicate an unused source ID while all decision-relevant citations remain unique. Alliance should stay clean and valid provenance should stay structurally clean apart from the required global duplicate-ID finding. The fresh alliance probe currently stays completely clean, whereas the current item checker gives the global duplicate-ID finding; these are different existing domain behaviors, not a proposed mismatch in fixture expectations.

## Independent boundary probes to keep separate

- **Alliance sensitivity:** (a) ambiguous reverse only, unique forward, as above; (b) same ambiguous ID on both directions; (c) ambiguous reverse plus a second reverse edge backed by a distinct unique source (the unique edge should suffice); (d) duplicate ID occurs only on an unrelated source, preserving clean reciprocity. These distinguish source ambiguity from edge absence and avoid globally poisoning unrelated witnesses.
- **Provenance sensitivity:** (a) duplicate source used by an otherwise valid record; (b) duplicate unused source; (c) broken predecessor with unique sources versus broken predecessor with an ambiguous citation; (d) another record/source uniquely cited alongside the ambiguous one. Make the expected treatment explicit: either source qualification is independent of structural chain validation, or the chain finding is gated by citation qualification. If structural findings remain, label them as assertions in the input, not as source-supported canon. Do not conflate `unknown` with `ambiguous`, and do not cascade an ambiguous source into every reference unless that is the declared diagnostic policy.
- Across probes, preserve both source rows and the original duplicate-ID error; never collapse, rename, choose a last-wins record, infer source-text content, or claim a citation is true. Source membership/uniqueness is not textual support.
