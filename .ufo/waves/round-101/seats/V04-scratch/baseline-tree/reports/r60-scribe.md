## Proposed distinction and calibration judgment

**Proposed policy: represent table load status separately from its rows.** Keep the primary file/parse/shape diagnostic. For checks whose conclusion requires entity-index completeness, emit a reference conclusion only when `entities.json` loaded as an array: loaded zero matches remains dangling; one remains resolvable; multiple remains ambiguous. When the entity table is unavailable, mark only entity-reference conclusions that depend on it as *unassessable because entities table unavailable* (or withhold them while clearly identifying that scope); do not silently convert unavailable into empty. Retain independent checks that do not depend on entity membership, including timeline event/dependency checks and source-ID checks against a successfully loaded sources table. Do not suppress findings merely because some other table is unavailable.

**CALIBRATION: GO, narrowly and conditionally.** Existing behavior creates a misleading equivalence: missing/invalid entity table is reported as `rows=[]` (`:45–51`), then absence diagnostics (`:143–149,193–205,248–261`) describe references as dangling just as if a complete loaded table had zero matches. The r59 nested duplicate gives a concrete affected case: table parse rejection followed by six dangling findings. Distinguishing lookup unavailable from lookup performed improves calibration of the checker’s input diagnostics; it does not establish any entity exists or is absent in the fictional world. Depth and coverage are unchanged; this does not resolve an entity ID when table data is unavailable.

## Prior-art constraint and falsifier

The r5 decision table expressly records missing/invalid `contradictions.json` as a required-table violation and says explicit `[]` means none while absence does not prove none (`knowledge/2026-10-12-lore-decision-table.md:44`); r5 observed missing or invalid `entities.json` followed by six dangling findings (`reports/r5-scribe.md`, table; raw source at `:45–51`). These are evidence of current behavior and an analogous absence/unavailability distinction, **not** a previously adopted entity-table suppression policy. R11 says zero *among screened entity rows* is dangling (`decision-table.md:116–123`); it does not define behavior when the entity table cannot be loaded. R13 likewise treats zero screened rows as dangling (`:135–143`). Keep those loaded-table rules intact.

Falsifier: paired replay shows that a missing/invalid/duplicate-unload `entities.json` is still reported as a definite dangling entity, or the proposed unavailable state suppresses a dangling finding for a successfully loaded table with zero matching rows. Also NO-GO if isolating entity-dependent checks suppresses independent dependency/source/schema findings, or if a pinned regression replay produces unexplained output changes outside dependent unavailable-table references. A minimal proof pair is unavailable entities table versus loaded `[]` (or loaded table lacking `mira`): the former retains load error and withholds only lookup-dependent absence conclusions; the latter reports dangling `mira`. Add a loaded unique/duplicate control to establish 1/2 behavior unchanged. The existing r59 nested case is a regression/cascade check, not a substitute for these paired controls.

## Risks and limits

- The r59 nested file has repeated `source_id` keys inside a claim (`fixtures/r59-nested-duplicate/entities.json`); the global object-pairs hook rejects the whole table (`check_bible.py:16–22,41–44`). R59 reports six resulting dangling findings. A proposed suppression would remove those six secondary claims while retaining the duplicate-member primary diagnostic; count only as cascade reduction, not six resolved fictional facts.
- Scope must follow dependency: entity-reference checks in relations, timeline, and provenance can be withheld when entity rows unavailable; source-reference checks still consult `sources` and must not be suppressed on that basis. Event/dependency validation uses timeline data and should remain independent unless its own prerequisites are unavailable.
- A loaded partial table is not necessarily known-world-complete. The distinction here is strictly whether the checker successfully loaded its input index; a dangling result means no matching row in that loaded input, not metaphysical or narrative absence.
- Do not conflate unavailable entity table with unavailable source table, source-text support, canon, chronology, or rights/permission. No claim about fictional-world absence follows either state.
