# Round 5 critic — falsification risks for the calibration claim

## Observations

The proposed claim in `.shokunin/lore/LOG.md` is deliberately narrow: document CLI behavior for isolated malformed-input cases while leaving `.shokunin/lore/corpus/fixtures/check_bible.py` unchanged. I found several ways the evidence could fail to establish the claimed calibration improvement.

1. **The evidence presently in scout reports is not reproducible from the repository.** `.shokunin/lore/reports/r5-loader-scout.md` and `r5-citation-scout.md` describe probes under `/tmp/lore-r5-loader-scout/` and `/tmp/lore-r5-unknown-source-ywo6rtii/`; they explicitly say these are temporary, uncommitted copies. The `r5-simplifier.md` also describes temporary copies, not committed input artifacts. A reader cannot replay these paths after the worker environment disappears. Meanwhile `.shokunin/lore/reports/r5-test-scout.md` lists proposed `.shokunin/lore/corpus/fixtures/r5-malformed/...` paths and says they must be made to exist; a proposal is not observed evidence. At inspection, `find .shokunin/lore/corpus/fixtures -maxdepth 2 -type d` has no `r5-malformed` directory. Existing `corpus/live/runs/20261012T155644Z`, `161753Z`, `162704Z`, and `163450Z` contain prior-round outputs, not the five round-5 malformed probes.

2. **“One mutation” does not mean “one diagnostic.”** In `.shokunin/lore/corpus/fixtures/check_bible.py`, when a table fails loading, `rows=[]`; subsequent relation/timeline checks still execute. The loader scout actually observed that deleting or corrupting `entities.json` produces six additional dangling-entity errors, so a table that says only “cannot load JSON” would conceal real output. Similarly, wrong top-level type empties that table and can cascade. A useful bounded table can name a primary diagnostic class, but must explicitly record secondary diagnostics (or state exactly that it only asserts presence of primary class and exit code). The phrase “diagnostic class” alone is not a complete expected output oracle.

3. **The proposed row-shape test is under-specified and may test the wrong branch.** Test scout proposes replacing a source row with a scalar. The checker reports `sources[i]: expected object` and skips that row. That is specifically a non-object-row case, not a missing/ill-typed required-field case; the latter follows a different branch and can have different downstream effects. Do not generalize one result as “row shape” broadly. Also distinguish `null`, scalar, and object missing required keys only if each is actually represented; otherwise explicitly bound the row to one concrete case.

4. **The table risks conflating an unresolved citation with source validity.** `r5-citation-scout.md` probes `entities[0].first_appearance`, whereas the LOG says “invalid citation” without fixing which citation field. The checker funnels several locations through `source()` but those diagnostics have different locations and potentially different row circumstances. The fixture table should state one exact field and ID, and must not imply it tests whether a source supports a claim: it only tests membership of an ID in `sources.json`. `corpus/fixtures/README.md` already explains citations as in-world record IDs, not verification of truth.

5. **“Preserved old outcomes” needs a meaningful baseline.** Existing fixture outputs under `.shokunin/lore/corpus/live/runs/` are transcripts, not a recorded checker hash / complete baseline replay manifest. The decision-table change alone should not change checker behavior, but asserting preservation requires explicit baseline commands and comparison scope. A test that merely reruns new cases cannot establish old outcomes were preserved. Do not use round-4 archived outputs as baseline: the rejected experiment has different checker behavior and inputs (`corpus/live/rejected-r4/`).

6. **A second person re-running the same committed command is not enough to prove independence if they inherit the expected answers or mutable inputs.** A verifier who reads the table first and then confirms its labels can share the author's interpretation error. Stronger evidence is a non-author executing the listed commands against committed fixtures, recording raw stdout/stderr and exit status before comparing with the table, and checking fixture hashes and checker identity. The fixture paths must be stable repo-relative paths, not worker `/tmp` paths. Protect inputs from accidental regeneration/edit during replay, or record hashes before/after. The intended “non-author” condition should include non-authorship of fixture construction and expected-output table, not merely being a different lane name.

7. **Portability and command exactness matter for loader rows.** Missing-file diagnostics include absolute paths and OS exception text; invalid-JSON diagnostics include parser offsets. Scouts already note this variability. Exact full-output equality is not a portable oracle. The table should say which parts are stable assertions (exit, filename, diagnostic prefix/class, count if promised) and which are environment-dependent. Give the repository-root working directory and exact `python3` command for each row; do not silently normalize away the only evidence of an incorrect fixture path.

8. **No independent round-5 replay is evidenced by the artifacts inspected here.** The current LOG plans a later verifier, and test-scout is a plan. The inspected reports do not establish that all committed rows have been replayed by a non-author. Calibration therefore remains unproven until the raw fixture set, table, and non-author replay agree.

## Recommendations (not observations)

- Keep the table claim bounded to five named inputs: clean control; missing required table; syntactically invalid JSON; valid non-array top-level value; one explicitly defined non-object row; and one named unresolved-source field (the LOG currently says one probe per class, so avoid adding cases silently). Clarify whether the five malformed classes count the citation row separately from row-shape.
- Commit actual minimal fixture directories (or another directly replayable artifact) and table together before asking for verification. Prefer copying the clean fixture and changing exactly the stated file/property. Avoid relying on temporary probe descriptions or archived stdout alone.
- State expected observations as exact exit status plus stable diagnostic assertions, and enumerate expected secondary diagnostics where they occur. If preserving whole output, scope it to a pinned environment; do not assert host-specific absolute paths/parser prose as invariant.
- Ask a non-author who did not prepare fixtures or expected results to run each exact repo-root command, capture raw stdout/stderr/status, inspect before/after fixture and checker hashes, and report mismatches without repairing the artifacts. The verifier should not author the expected table.
- Retain the existing clean/contradictory/reciprocal fixture commands as the explicit prior-outcome comparison if “preserved old outcomes” remains part of the claim. Compare statuses and relevant stable diagnostic sets; do not infer preservation from unchanged checker source alone.
- Until these conditions are met, characterize the move as a proposed clearer reference/table, not demonstrated calibration improvement. A table that accurately documents several malformed cases could improve calibration, but the present temporary probes and plan do not independently establish reproducibility or calibration.
