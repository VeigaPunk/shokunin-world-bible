# Round 56 critic — holder-reference ambiguity diagnostic

## Independent judgment

**GO, narrowly, for a reference-local ambiguity finding; calibration gain is modest and conditional.** A schema-valid repeated holder ID is already rejected globally, but the current item loop silently invalidates the chain at the exact field without saying why. That omission costs operators localization, rather than coverage of duplicate entities themselves. A local diagnostic can identify the unresolved provenance reference while preserving the existing global duplicate finding and raw record. It must not select a duplicate row, assert a holder, or claim actual custody. The report should remain a structural input ambiguity, not an assertion that the text or world is ambiguous.

## Calibration limits and risks

The proposed gain is **not** “more correct chain validation”: current logic already disables chain checking after an ambiguous holder. It is only clearer attribution at the referenced field (and potentially each affected field in a record). Its utility is weaker than r24’s because the global duplicate plus suppressed chain can already alert an attentive reader; a local line may add noise, especially if many provenance rows reuse the duplicate ID. Avoid reporting one ambiguity per occurrence if that floods output; if implemented, report each distinct affected field occurrence, with exact location and ID, and retain the single global duplicate. Do not collapse multiple occurrences into an item-wide claim that any holder is ambiguous without pointing to the raw field.

The unique-ID control must retain the existing chain-break and other diagnostics unchanged. Duplicate `to_holder` and `from_holder` probes must each show only their own new local ambiguity while chain checks remain gated; a record with both should not mask unrelated malformed-tick/source findings. Count-zero references must stay dangling, not be relabeled ambiguous. Only schema-admitted duplicate entity rows count; malformed rows must not create an ambiguity signal. Duplicate item IDs are a separate pre-existing chain gate and should not be mislabeled as holder-reference ambiguity. Keep the global duplicate-ID message and provenance arrays byte-for-byte; no inferred repair, deduplication, or row-order-dependent holder selection.

## Falsifier

**NO-GO if a minimal, schema-valid `to_holder`-only and `from_holder`-only pair cannot show a distinct, actionable field-local reason for chain suppression beyond the existing global duplicate finding, or if either new message changes the unique-ID control’s chain-break output / lets comparison proceed across ambiguity.** Also reject the calibration claim if a malformed duplicate is what triggers the message, if unaffected unique holder references receive it, or if the new output implies which duplicate row is intended. The declaration’s paired probes and unchanged 95 raw outputs / 474 JSON bytes are necessary validation, not results observed by this critic.

A newly local message is structural validation only. No checker, fixture, README, LOG, or shared decision-table changes are recommended by this critic; no probes or candidate outputs were run in this review.
