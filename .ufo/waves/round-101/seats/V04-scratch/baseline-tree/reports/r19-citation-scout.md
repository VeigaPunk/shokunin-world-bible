# Round 19 citation scout — tick input, source text, and canon

Scope: read-only identity and evidence-boundary review of the declared negative-tick occupancy move. This report separates observed checker/input behavior from recommendations. No checker, fixture, shared document, or commit was changed.

## Raw observations

- In `check_bible.py`, the timeline schema screens `tick` as an integer (`type(value) is int`), but the timeline validation later reports `timeline[i].tick: must be nonnegative` for a negative value. The event row remains in the screened timeline data and is still considered by later checks. In the current occupancy code, `slot = (entity_id, tick)` uses the supplied integer directly; there is no normalization or alternate time lookup.
- The checker has separate identifier spaces for timeline-event `id`, entity IDs used by `entity_id`/`place_id`, and source IDs used by `source_id`. A tick is a numeric field, not an identifier and not a citation. `depends_on` refers to event IDs; its inversion check compares their numeric ticks. It does not interpret event-description wording to assign a time.
- The checker checks source-reference identity/status by looking up `source_id` in `sources.json`. It does not load source text, parse prose such as “first bell,” “later,” or a date, or test whether a source supports the event's tick, location, or description. Event `description` is required text, but the checker does not use it to determine occupancy or chronology.
- The fixture README characterizes ticks as nonnegative integers in an invented world's local sequence, not absolute dates. That describes the data convention; it does not map a source-text phrase onto a numeric tick. A numeric fixture tick is therefore an input assertion/convention, not independently established source time or canon truth.
- At inspection, the round-19 LOG declares negative-tick suppression as a candidate and says the paired CLI result is not yet observed. I did not find a round-19 paired fixture/result to cite. The code inspection alone shows current raw negative-tick use; it is not evidence that a particular pair actually emits `double-booked`.

## Recommendations (not observations)

- Describe any experiment as constructed timeline **input**: e.g. `tick: -1` versus `tick: 0`, with the rest of the paired rows held fixed. Do not call the negative tick a source-text time, date, “before the story,” impossible time, or canon-false event. The checker can validate its own nonnegative-integer convention, not adjudicate whether a fictional report could describe such an event.
- Keep `id`, `tick`, and `source_id` terminology distinct. A unique `source_id` establishes only unique reference resolution. It neither endorses the input tick nor proves that the cited text contains that time. If a fixture's source text includes a temporal phrase, quote/map that exact wording separately and describe it as an authored report, not as a numeric conversion unless the text explicitly provides one.
- Event descriptions in new paired fixtures should say “Fixture input only; no narrative/source-text time claim.” Preserve source IDs only as required fixture structure; avoid writing a description that implies the source attests to the chosen tick.
- State the intended checker result narrowly: preserving the invalid-tick diagnostic/raw row while withholding a definite occupancy comparison at an invalid numeric tick would be a checker-calibration choice. It would not establish that the event did not occur, that the source is wrong, or that no in-world conflict exists. Conversely, a `double-booked` message from raw invalid input does not establish two canon events or source support.
- Use valid nonnegative same-tick known-place controls to demonstrate the checker still reports the bounded input pattern; if testing a known pair around invalid rows, ensure all event dependencies and tick comparisons do not add unrelated inversion findings. Report exact CLI observations only after running the constructed inputs, and do not attribute them to a source-text/canon claim.
