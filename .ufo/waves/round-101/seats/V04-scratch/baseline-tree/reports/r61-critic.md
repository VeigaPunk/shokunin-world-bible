## Observed behavior versus proposal

**Observed in current source:** failure/invalid source data is collapsed into empty admitted rows for membership purposes; all those direct sites can say unknown, and the ledger can say no resolvable source. Valid empty sources produce the same zero-count conclusions. This is structural input behavior, not evidence from source text. No r61 candidate implementation or matched r61 probe was available to me, so these are source-derived expectations, not executed r61 output claims.

**Proposal under review:** keep the parser/load diagnostic, but track a source-table status as loaded/unavailable (including malformed top-level value as unavailable). If unavailable, withhold only conclusions computed from source membership/count: direct unknown/ambiguous source-ID claims and the ledger’s “no resolvable source_id” conclusion when it is solely based on that unavailable index. Preserve loaded empty as available, and preserve its unknown results; preserve all known source-ID ambiguity when an array loaded. Preserve the ledger event pointer/cardinality, ledger shape/different-side checks, entity/relation/timeline checks independent of source membership, and all row-local schema errors. A parsed array containing rejected malformed rows remains “available” under this narrow contract, just as r60 explicitly treats parsed entity arrays as available; a reference found only in rejected rows can still appear unknown. Do not broadly skip timeline, provenance, or ledger checks.

A possible weaker alternative is to retain affected-reference locations as explicitly `unassessable` rather than omit them. Either policy needs an actionable primary load error, must not say CLEAN, and must not label unavailable input as empty or absent. Simply setting `sources=[]` and early-returning from `source()` is insufficient: downstream callers use returned statuses (`:217-221`, `:251-253` in relevant checker logic) and could change chain/witness qualification. Trace those consumers before implementation.

## Novelty and utility challenge

There is precedent for both halves of the reasoning, which makes the material-gain claim nontrivial. R5/r31/r32 document source-ID ambiguity and malformed-source admission consequences; those address multiplicity or retained-row screening, not a failed whole source index. R39’s exact ledger case is particularly close: `.shokunin/lore/reports/r39-executor.md` observed a uniquely resolved ledger event with missing `source_id`, yielding both a ledger-local “no resolvable source_id” and timeline-local unknown source; `.shokunin/lore/reports/r39-axis-adjudicator.md` treats this as an existing zero-source branch exercised, not a new checker rule. It is not an unavailable-table case: its `sources.json` is loaded. R60 admitted the analogous distinction only for `entities.json`, and explicitly left source/timeline table failures out of scope (`LOG.md`, R60 closure and R61 declaration). Therefore the source-table cascade is new as a *table-availability calibration hypothesis*, but the status phrase and ledger branch are not themselves new.

The tangible benefit would be preventing multiple “unknown” conclusions from being presented as if a failed source index had been successfully searched. Yet those per-reference lines are useful affected-reference hints for repair, and the load error alone does not tell the user which rows depend on sources. R60 judged loss of six such hints acceptable for entities because matched loaded-empty/partial controls and independent-fault tests showed a tightly scoped output distinction. That is not automatic justification for source suppression: sources fan out through more contexts, and `source_status` affects derived behavior (e.g. provenance chain eligibility and sourced reciprocal alliances). Broad suppression can hide real independent structural errors or inadvertently qualify a claim/witness. There is currently no matched r61 replay demonstrating exact scope or acceptable hint loss.

## Concrete falsifier / required probe

Use a clean fixture pair and keep every non-source byte identical. Run at least: (1) unavailable `sources.json` via missing file, malformed JSON, duplicate member, and non-array value; (2) loaded empty `[]`; (3) loaded partial sources; (4) loaded ambiguous ID. Include direct relation/entity citations, a unique-event ledger endpoint, provenance with otherwise malformed holder/tick chain, and an allied reciprocal candidate whose source status is relevant. Capture stdout, stderr, exit, all diagnostics, and hashes. The proposed distinction survives only if unavailable retains its parser error and withholds/marks only lookup-dependent source conclusions, while loaded empty/partial/ambiguous controls retain their existing findings. In the unavailable case, ledger event existence/cardinality and differing-claim/shape findings, negative timeline tick/dependency errors, entity/relation structure, provenance field/holder/tick errors, and source-independent alliance structure must remain. Ensure the unknown source result cannot accidentally be treated as `unique` or as a valid reciprocal witness merely because its diagnostic was suppressed. Compare old/current output for the pinned corpus and enumerate every changed path/tuple. Any hidden independent error, any unavailable result reported CLEAN/resolved, any loss on loaded-array controls, or an implicit empty-as-available policy falsifies safety/material calibration.

## Verdict and epistemic boundary

**NO-GO on material admission on the current critic evidence; GO only to a narrowly gated experiment, not implementation or acceptance.** The source-index availability distinction is plausible, but the r60 entity result cannot be generalized across callers whose status participates in downstream qualification. The currently available evidence establishes a code path and a credible hypothesis, not a measured material improvement without collateral. If the matched controls and independent-fault probes above pass, a later adjudicator may admit a source-only calibration gain; if safe scoping requires suppressing more than source-membership conclusions or loses useful affected-reference visibility without a clear status replacement, reject it.

This checker validates supplied IDs and structure, not source-text support or truth. Missing membership in a loaded source table is not proof that a source does not exist outside the input; an unavailable table proves no membership conclusion at all. Neither diagnostic nor suppression establishes fictional-world facts, chronology, testimony truth, canon, copyright status, rights, license, or permission. No claim here resolves narrative canon or authorial intent.
