# Round 56 citation scout — holder-reference ambiguity boundary

## Independent calibration judgment: conditional GO for a narrowly local diagnostic, with materiality caveat

The proposed rule is about resolving a provenance field against the schema-admitted entity rows, not about proving custody. It is a defensible calibration move only if the diagnostic explicitly says *ambiguous entity ID in input* and chain comparison remains withheld at that point. The global duplicate-ID finding is not a sufficient substitute for a precise field location: a reader otherwise has to cross-reference duplicate IDs against each provenance record to discover which holder assertion is affected. This is modest operator-facing calibration, not new coverage or deeper source knowledge. Since no candidate was built or independently replayed in this scout task, this is a recommendation, not an implementation verdict.

A minimal candidate would report each non-null holder reference whose ID count exceeds one at `entities[i].provenance[j].from_holder` and/or `.to_holder`, preserve the global duplicate finding and every raw record, and keep existing chain suppression. A unique-ID holder reference can still participate in the structural chain convention; that does not establish actual possession. An ambiguous reference must not be arbitrarily resolved to the first/last row, nor produce an apparent chain break against an unknown selected row. Null `from_holder` on the initial record is not a reference and should not be diagnosed. A malformed duplicate row excluded by schema screening is not a second admitted target (Round 26); a display-name homonym with different IDs is irrelevant.

## Source, custody, canon, and rights boundary

`source_id` is only a locally resolvable fictional record ID. The checker does not open or interpret any referenced source text (provenance checker calls `source()` at `check_bible.py:186-194`); no result here establishes textual attestation, source authenticity, authorial canon, or rights/permission. The structured keys `from_holder` / `to_holder` are assertions encoded in fixture data, not observations of actual custody. Even a structurally unique holder ID plus a valid chain says only that the authored rows satisfy the selected internal convention. Duplicate rows likewise do not establish multiple actual people or holders. Do not infer acquisition, transfer, retention, loss, theft, ownership, or absence from these fields or diagnostics. Do not infer anything about real-world sources or rights from fictional citations or the separate reference ledger.

## Falsifier and collateral

**Falsifier:** if a candidate adds per-field ambiguity but (a) selects a duplicate row, (b) permits chain comparison through that ambiguous holder, (c) changes unique/dangling/null behavior, or (d) merely restates an already sufficiently actionable global finding without an operator-relevant distinction, reject the calibration claim. To establish GO beyond this scout recommendation requires paired schema-valid holder-duplicate probes—one duplicate ID referenced only in `to_holder`, one only in non-null `from_holder`, plus unique and dangling controls—and exact replay of the pinned 95 existing fixture raw stdout/stderr/exit tuples and 474 fixture JSON bytes. The expected ambiguous diagnostic must be local, and chain evaluation must remain masked, while global duplicate and raw provenance stay intact. A malformed duplicate is not an admissible ambiguity test.

**Anticipated collateral:** one duplicate holder ID referenced in several records can produce multiple local diagnostics in addition to its single global duplicate-ID diagnostic. If both `from_holder` and `to_holder` are duplicated in one record, expect two field-local findings, not one collapsed message. Existing unrelated timeline/relation references may also diagnose the same duplicated ID; retain them rather than suppressing cross-consumer findings. Item-ID duplication already disables that item's chain check (`check_bible.py:144`), so a holder diagnostic must not imply its chain was otherwise evaluated. Keep raw records and count schema-admitted rows only.
