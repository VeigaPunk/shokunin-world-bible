# Round 3 schema scout: missing files and contradiction ledger

## Evidence from the current checker and fixtures

- `.shokunin/lore/corpus/fixtures/check_bible.py` defines exactly four sections in `FIELDS`: `sources`, `entities`, `relations`, and `timeline`. `check()` iterates each section and reads `<section>.json`; `OSError`, invalid UTF-8, and JSON decode errors append a `cannot load JSON` violation and substitute an empty array. A non-array adds `expected array`. Thus the existing contract treats every listed JSON file as required, not as an optional section.
- I copied fixtures to temporary directories and removed files to probe behavior (repository fixtures were untouched). Removing `entities.json` from `consistent` exited 1 and reported the missing file plus dangling entity references; removing `sources.json` exited 1 and reported missing file plus unknown citations; removing `relations.json` or `timeline.json` exited 1 with a missing-file violation. Removing an unrecognized `contradictions.json` exited 0. These are runtime observations of current behavior.
- All four existing fixture directories currently contain the same four filenames: `consistent/`, `contradictions/`, `ally-reciprocal/`, and `ally-one-way/` each have `entities.json`, `relations.json`, `sources.json`, and `timeline.json`. See `.shokunin/lore/corpus/fixtures/`.
- The existing `contradictions/` fixture seeds structural conflicts in `relations.json` (dangling `missing-map`) and `timeline.json` (dependency on later `later`; same-tick Mira at `tower` and `harbor`). The checker reports those via its relation/timeline passes. It has no explicit contradiction-record section now.
- `consistent/` and the alliance pair also have no ledger today. The alliance fixtures are deliberately minimal: `ally-reciprocal/` and `ally-one-way/` have two faction entities, their relation records, a source, and `timeline.json: []`.
- `.shokunin/lore/corpus/fixtures/README.md` documents the four checker commands and the fixtures’ current exit behavior; it does not establish an optional-file convention.

## Assessment / recommendation (not observed behavior)

A mandatory fifth `contradictions.json` in **every** fixture is compatible with the checker’s existing required-section pattern, and it makes missing-ledger behavior unambiguous: after adding the section to `FIELDS`, omission is an error just like omission of the other four files. It is not clearly the *smallest* safe design for round 3’s declared claim, which requires a valid explicit ledger for the contradictory bible and preservation of clean/alliance fixtures. Requiring four files and empty arrays for fixtures with no ledger introduces fixture churn without testing a distinct claim.

Recommended narrow design: make the new section required only for the `contradictions/` fixture (which must contain its valid records), and ensure a malformed/missing ledger there fails with a ledger-specific diagnostic. Keep the clean/alliance fixtures’ behavior unchanged unless the task explicitly chooses a universal fifth-file schema. If implementation instead elects universal mandatory schema, add `contradictions.json` (probably `[]`) to all four existing fixture directories and test that omission fails; do not silently make missing files optional by generic fallback. This recommendation preserves the round-3 scope while retaining strictness where the ledger is asserted.

One implementation decision needs to be explicit: whether the ledger is a universal bible section or a round-3 test artifact specific to the contradictory fixture. The current checker has no fixture-name semantics, so a narrowly conditional requirement would need either an explicit checker option/schema mode or a universal required file. A universal empty ledger is mechanically simpler in the current generic section loader; a conditional rule avoids edits to unrelated fixtures but adds special-case logic. Based on the declared current claim alone, I favor the narrowly scoped requirement and would avoid adding generic optional-file semantics.
