# Round 7 critic: duplicate source IDs and citation qualification

## Observed evidence

- In the checked-out `.shokunin/lore/corpus/fixtures/check_bible.py`, `index(section)` (lines 45–51) appends a duplicate-ID violation but unconditionally assigns `result[row['id']] = row` afterward. Thus later rows replace earlier rows in the returned dictionary. For sources, downstream checks use dictionary membership (`source()` at lines 61–63; alliance witness membership at lines 128–134; provenance source membership at lines 193–196). Those checks do not inspect which source record won or whether its title/reliability note supports a claim.
- Replayed the unique reciprocal fixture from repo root: `python3 .shokunin/lore/corpus/fixtures/check_bible.py .shokunin/lore/corpus/fixtures/ally-reciprocal` printed `CLEAN: schema, citations, relations, timeline; 0 violations` (exit 0). The fixture has a single `harbor-compact` source and reciprocal `allied_with` rows both citing it.
- Made a temporary copy of `ally-reciprocal` at `/tmp/r7crit-2_xrnrrz/dup`, added a second `sources.json` row with the same `harbor-compact` ID but a changed title, and ran `python3 .shokunin/lore/corpus/fixtures/check_bible.py /tmp/r7crit-2_xrnrrz/dup`. It exited 1 and printed only `VIOLATION: sources[1].id: duplicate sources id 'harbor-compact'` and `1 violation(s); no canon changed`. It emitted no ambiguity diagnostic for either relation, yet the reciprocal edge still qualifies by `candidate['source_id'] in sources`. This is a concrete counterexample to any claim that current duplicate IDs already make references non-qualifying or produce local ambiguity findings.
- The same mechanism applies to item provenance: each valid record calls `source()` and checks only `source_id not in sources` (`check_bible.py:193–196`). The checked-in valid fixture `.shokunin/lore/corpus/fixtures/item-chain-valid/entities.json` cites `courier-log`; duplicating that source ID leaves it a dictionary member. No source-record field is consumed by the chain logic.
- This is validation of identifier resolution only. Even a unique ID does not prove that a source text exists, contains the cited assertion, is reliable, or establishes canon truth. `sources.json` is metadata; the checker never opens or evaluates source text.

## What the evidence does and does not establish

Observed: duplicate source IDs trigger the existing duplicate violation; the source dictionary is last-row-wins; reference checks still treat that ID as present; and the current diagnostics do not identify affected references as ambiguous. Because all current source consumers use membership, not source metadata, the actual semantic effect of swapping the duplicate rows is indistinguishable for those consumers today. “Last-wins” is an implementation fact, but do not overstate it as a demonstrated change in citation truth or current rule outcome beyond membership qualification.

The temporary test adds only one duplicate source row to the reciprocal fixture. It does not establish all possible diagnostic-cascade behavior, nor replay every source-bearing field (claims, first appearance, timeline, relation, provenance, contradiction event references). Those remain untested here. A blanket promise of one ambiguity error per reference is especially risky: a single duplicate may be cited in many places, and the old duplicate-ID violation plus local findings would multiply output. Conversely, suppressing all downstream findings can conceal references whose status really is ambiguous. Specify whether diagnostics are per duplicate ID, per reference, or both; deduplicate them deterministically and test an ID cited in multiple sections.

## Critique / proposed checks (not implemented)

1. Define uniqueness as a property of the source-ID index, not as evidence that a citation is textually supported. Build counts (or an unambiguous-ID set) and let a reference qualify only when its ID occurs exactly once; keep both input rows and the duplicate-ID finding. Avoid whichever-row-wins semantics for qualification.
2. Avoid noisy cascades: retain the duplicate-ID diagnostic and choose a bounded, explicit policy for references to that ID (for example, one local `ambiguous source id` finding per distinct reference location, or a summarized list). Do not describe that as a source-support check.
3. Probe both alliance and provenance consumers with paired unique/duplicate fixtures, plus at least one ordinary source reference (entity claim or first appearance) and a repeated ID cited from multiple locations. Verify exact outputs and ensure unique-ID clean cases remain clean.
4. Distinguish source-ID uniqueness from source truth. A unique in-world ID is resolvable, not proof of textual backing, reliability, or correctness; making an ambiguous ID non-qualifying is a conservative validation convention, not a truth adjudication.

The round-7 claim is supportable as a narrow calibration target only if non-author replay demonstrates the new qualification policy and bounded diagnostics. This critic report observes current behavior; it does not assert that a proposed checker change has been implemented or verified.
