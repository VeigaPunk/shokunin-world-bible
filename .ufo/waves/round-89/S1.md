## Findings & named debt

**A — complete same-record cause summary.** In `corpus/fixtures/check_bible.py:242-295`, `record_stop_cause` is a scalar. Its first assignment wins (`or` at invalid `from_holder`, invalid `to_holder`, dangling holders, ambiguous-holder group, invalid `source_id`, unknown source, and unavailable-source branches). The arming point is `:296-301`, where `first_stop` is set only if absent. Exact candidate: replace the scalar with an ordered `record_stop_causes` list; append each cause at the same branches; keep the ambiguous-holder references as their existing one grouped cause; join with `'; '` at `:299`, leaving `record_label`, first-stop latching, and later disclosures unchanged. Do not include ambiguous source status: `:294-295` marks it for comparison qualification but does not make the record invalid. Leave the unexpected-key branch `:208-234` alone; it exits before these checks and cannot promise causes it never evaluated.

The measured in-corpus delta is only `r87-probe-multi-invalid`, with the summary changing from `ambiguous holder identity from_holder 'vault'` to `ambiguous holder identity from_holder 'vault'; unknown source 'ghost-source'`; its five findings and exit 1 remain unchanged. This is an enumerated stdout-only tuple delta. Risk: appending every local diagnostic, or claiming completeness for shape-rejected records, would overstate the causes that actually latch comparison suppression. Semicolon joining avoids ambiguity with commas inside grouped holder causes. This matches the list/join approach in X2’s independent summary-only patch; that patch was read, not applied here.

**B — qualify findings against unresolved holder identities.** The resolved entity index is built only from schema-valid rows (`:65-76`, `:157-160`), so a raw duplicate with one schema-rejected row can leave a resolved count of 1. A provenance record can then pass holder validation and emit a definite finding against the surviving index identity. Preserve raw entity IDs rejected by schema validation during the row loop (only nonempty string IDs); a helper can return unresolvable when the resolved count is not exactly one or that ID also had a schema-rejected row. Do not arm this on an unrelated rejected entity row.

Apply the predicate at all three comparison sites: tick order `:305-306` and adjacent-record chain break `:307-308` should inspect the transition endpoints (`previous_holder`, current `from_holder`); first-record non-null `from_holder` `:309-310` inspects that `from_holder`. Combine the holder predicate with the existing `chain_has_ambiguous_source` guard so the prefix appears only once; preferably state the holder-resolution reason explicitly. Normal count-zero and count-greater-than-one holders are generally stopped earlier by record validation; the regression path that reaches comparison is the count-one-but-raw-schema-rejected case. On the existing 149, the prototype changes no tuples. On F3’s unresolved fixture it adds the structural qualifier to one chain-break line while preserving the control. A synthetic two-row probe also qualified the tick-order and adjacent-chain-break findings when their expected/current transition identity was unresolved, and qualified the first-record branch.

Risk: global qualification (e.g. because any entity row failed schema) would over-qualify unrelated checks. Tick order is about ticks rather than identity; if it is included per the seat request, only qualify when a holder identity belonging to that same compared transition is unresolved. Count != 1 is a defensive condition at these sites, not evidence to continue a comparison after ordinary validation has already stopped it.

**C — FN-1 cause wording.** The requested cause-building sites are dangling `to_holder` `:255-258`, dangling `from_holder` `:267-270`, and unknown `source_id` `:287-293` (cause assigned at `:290`). The prototype adds `(absent from the resolved index)` at these cause builders. It changes three existing fixture outputs, all source-first-stop tail disclosures; violation counts and exits are unchanged. There is no existing provenance first-stop in the 149 whose cause is a dangling holder. `source_status` is `unknown` only when the source table loaded (`:97-108`), so unavailable tables must retain their separate wording.

Important distinction: the simple suffix is true for both an ID absent from the raw JSON and an ID present only on a schema-rejected row, but by itself does not tell those two apart. B3 reproduces both cases with identical current cause strings. If C1 means a positive raw-presence distinction, retain raw IDs during parsing and say `present in raw ... but absent from the resolved index` for rejected rows versus `absent from raw ... and absent from the resolved index` only when the table loaded and the ID was not present. E1 proposes this stronger form. The ordinary diagnostics from `source()` at `:103-109` (notably `:106`) and dangling-entity checks at `:255-270` are separate from the stop-cause strings; changing only the cause summary leaves their current `unknown in-world source` / `dangling entity` text. Decide whether the requirement is cause-only or consistent wording at both layers. Never call an unavailable table evidence of raw absence.
