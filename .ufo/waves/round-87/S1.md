### Branch map

- **Admitted rows / absent property.** The block iterates only entity rows retained after the row-shape gate (`check_bible.py:65-76,171`). An entity without the `provenance` key takes the silent `continue` at `:172-173`; `consistent/` is a clean no-provenance control (M1). Rejected raw entity rows never reach this block.
- **Wrong entity kind.** Any present `provenance` on `kind != 'item'` emits `entities[i].provenance: only valid on item entities` (`:176-177`) but does not skip the rest of this item's provenance validation. `r61-independent-empty` and `r61-independent-unavailable` each exercise it (M5–M6). The gate also initializes `can_check_chain=False` for this kind (`:183`).
- **Non-array provenance.** Emits `...provenance: expected array` and continues before initializing chain state or visiting records (`:178-180`). **No active fixture.**
- **Initial state / initial assessment gate.** `previous_holder` and `previous_tick` start `None`; `can_check_chain` starts true iff the source file loaded as an array, this row is an item, and this entity ID has exactly one admitted row (`:181-185`; ID counts at `:157-160`, source availability at `:41-63`). The other two flags start false: ambiguous-source prefix not yet required, and no holder-ambiguity notice emitted. Non-item is covered by M5–M6, source-unavailable is present in M6 but co-occurs with non-item, and the independent **eligible item + unavailable sources** case has no fixture. A duplicate own item ID with provenance also has no fixture. These preconditions suppress chain comparisons silently; there is no initial per-record “unassessed” notice.
- **Non-object record.** Emits `provenance[i]: expected object`, resets both previous values to `None`, latches `can_check_chain=False`, then skips the remaining record (`:188-192`). **No active fixture.**
- **Object with wrong key set.** Any key set other than exactly `{tick, from_holder, to_holder, source_id}` emits the exact-key diagnostic, resets both previous values, latches false, and skips remaining record checks (`:193-198`). **No active fixture.**
- **Tick validation.** `type(tick) is not int` (so bool is rejected too), or `tick < 0`, emits the nonnegative-integer diagnostic and marks the record invalid (`:199-207`). Invalid-record handling then resets both previous values and latches false (`:243-246`). **No active provenance fixture** for invalid tick; timeline tick fixtures do not exercise this branch.
- **Holder field shape.** Non-null `from_holder` that is not a nonblank string emits its required-null-or-nonempty diagnostic and invalidates the record (`:208-210`); non-string or blank `to_holder` emits its required-nonempty diagnostic and invalidates it (`:211-213`). The later `from_holder` validation repeats the invalid state but does not emit a second message (`:221-223`). **No active fixture** for either malformed shape.
- **Holder identity resolution.** For nonblank holder strings, count 0 emits `dangling entity` and invalidates; count 1 is accepted; count >1 emits `ambiguous entity`, sets `record_holder_ambiguous=True`, and invalidates. `to_holder` is tested at `:214-220`; non-null `from_holder` at `:224-230`. Dangling references in both fields are exercised together by M5–M6, but on a non-item and a one-record chain. **No active fixture** exercises either ambiguous-holder direction. Counts use admitted entity rows; no row is selected (`:157-160`).
- **Ambiguous-holder disclosure.** If either holder count is >1 and no notice was emitted earlier for this entity, one record-local notice says continuity and tick-order checks are unassessed “at this and all later records”; it then latches `holder_ambiguity_notice_emitted=True` (`:231-233`). Later ambiguous holder references still get their local field error but no second notice. No active fixture exercises this. The non-fixture r85 replays M12–M15 observe the current one-notice behavior.
- **Source field and status.** Blank/non-string `source_id` emits the required-nonempty diagnostic and invalidates (`:234-236`); **no active fixture**. A nonblank ID calls `source()` (`:237-242`; helper at `:97-109`): `unknown` emits local unknown-source and invalidates, `unavailable` emits no local membership finding and invalidates, `unique` leaves the record valid, and `ambiguous` emits local ambiguity but leaves it valid while permanently setting `chain_has_ambiguous_source=True`. Unique is exercised by M2–M3, unknown and unavailable by M5–M6 (in non-item records), and ambiguous by M4. M4 has no chain discrepancy, so the ambiguous-source prefix on a chain finding is **not** covered. `source_status` means index membership only; it neither authenticates nor substantiates a source.
- **Any invalid record.** After all field checks, any `valid=False` path resets both previous values, latches `can_check_chain=False`, and continues (`:243-246`). This includes malformed values, dangling holders, bad ticks, unknown/unavailable sources, and ambiguous holders. No subsequent valid record can re-enable the gate. M5–M6 execute invalid holder/source paths but have only one record; no active fixture demonstrates reset followed by a later valid record. Historical `r85-masked-ambiguous` M13 does demonstrate a valid later record after the holder-ambiguity latch.
- **Comparison gate skipped.** A structurally valid record with `can_check_chain=False` makes no continuity or tick comparison (`:247`), but still reaches the unconditional previous-value assignments (`:255-256`); the flag remains false, so these values never resume assessment. Initial ineligibility and invalid-record latching have no generic per-record disclosure. M13 demonstrates a valid post-latch record with no chain comparison; it is not under `corpus/fixtures/`. No active fixture covers this transition.
- **First eligible record.** With `can_check_chain=True` and `previous_tick is None`, a non-null `from_holder` emits the first-record chain-break finding (`:247-254`). **No active fixture** exercises it; the valid control starts with null `from_holder` (M2).
- **Later eligible records.** When `previous_tick is not None`, `tick <= previous_tick` independently emits the provenance tick finding (`:248-250`), and `from_holder != previous_holder` independently emits a chain-break finding (`:251-252`). Both are qualified with `input-structural finding, not sourced-canon; ` after any ambiguous source citation in this item's records. The wrong-holder path is exercised by M3, with a unique source; no active fixture exercises equal/decreasing provenance ticks, both comparisons failing together, or either qualified/prefixed finding. A comparison finding itself does **not** reset values or latch the chain off; the current broken fixture breaks only on its final record, so does not test a later comparison after a break.
- **Successful record state update.** Every valid record stores its `to_holder` and `tick`, including when comparisons are disabled; comparison diagnostics do not prevent this (`:255-256`). M2 exercises normal updates; no active fixture verifies continued checking after a comparison mismatch.
