### Normative contract for both M1 and M2

M1 and M2 are alternatives, but each must independently satisfy the same contract and acceptance cases. Do not merge divergent output semantics. The inventory is declared in each map; a caller-supplied `--expect-rows` alone is not a substitute.

**Inventory format and row classes.** Add exactly one inventory block to each claim-excerpt map, with this exact table shape and lower-case values:

```markdown
## Support inventory

| row_class | expected_rows |
|---|---:|
| json-fact | 14 |
| editorial | 8 |
| total | 22 |
```

For r87, use `json-fact=14`, `editorial=8`, `total=22`. For r88-m3, use `json-fact=10`, `editorial=0`, `total=10`. Every parsed support row must carry a `Support class` cell with exactly `json-fact` or `editorial`; do not infer class from the ID prefix or table position. A table counts as a support table only when its header identifies the fact ID/claim pointer, support class, excerpt path, delivery mode, and anchor; span must be declared in a span column or path locator. If a header loses a required role, do not guess and do not parse that table as support rows—let the inventory mismatch report it as exit 1. Require one inventory entry for each class and `total == json-fact + editorial`. Count fact-table rows only: excerpt-declaration rows and prose bullets are not support rows. In particular, the two r88 Spence comparison bullets remain outside this receipt and are not an invented pair of editorial fact rows.

Parse the inventory independently from fact tables. Compare the declared counts with the number of parsed rows by class and total. A valid inventory with a renamed/unrecognized fact-table header or a dropped section must yield parsed counts below expectation and fail; it must never silently pass because some other table still parsed. The inventory table itself must not be inferred from the fact-table parser. Missing/duplicate/malformed inventory or count inconsistency is an inventory failure (exit 1), not a pass.

**Receipt and map wording.** Print a row-inventory split, using parsed/declared counts, with explicit labels equivalent to:

```text
ROW-INVENTORY JSON-FACT-ROWS 14/14; EDITORIAL-ROWS 8/8; TOTAL-ROWS 22/22
```

Also print source-support only for `json-fact` rows in `verbatim` or `translation` mode; report editorial anchor checks separately, and preserve separate retelling-only and mode counts. A retelling row must not enter source support. Report `DISTINCT-ANCHORS` as unique `(resolved excerpt path, exact anchor)` pairs over parsed rows, and `DUPLICATE-ROWS` as repeated semantic row signatures (support class, JSON pointer/editorial subject, excerpt path, span, mode, anchor; exclude display ID so a copied row with a renamed ID is still caught). Also report duplicate IDs. Repeated anchors across distinct facts are not, by themselves, duplicate rows or failures.

Update both maps, both cluster READMEs, and `corpus/tools/README.md`. The r87 map and README must say plainly that its support receipt counts **14 JSON-fact rows + 8 editorial rows = 22 total rows**, not 22 individually checked JSON facts. Preserve the disclosed crosswalk: two JSON obligations are note-only and some pointers are co-mapped; do not describe the row receipt as a raw JSON-obligation census. The r88 map/README must state **10 JSON-fact rows + 0 editorial rows = 10 total support rows**; its two symbolism comparisons are separate prose and excluded. Document warning, failure, inventory, and exit behavior in the tools README.

**WARN vs FAIL.** Emit each diagnostic with a literal `WARN:` or `FAIL:` prefix.

- `WARN`, exit 0 permitted: a `paraphrase`/`summary` row has no anchor hit, provided its declared mode agrees and its span is syntactically valid; and a map excerpt-mode declaration has no support fact row referencing that excerpt. For an unreferenced declaration, report path and declared mode; do not count it in fact-row support or `MODES N/N`. If the unreferenced excerpt has an inline mode and it conflicts with the map declaration, that is a mode failure, not merely a warning.
- `FAIL`, exit 1: missing source-support anchor; any source-mode anchor hit outside the declared inclusive span; missing/invalid span; mode missing or mismatched; excerpt missing or outside the cluster; inventory absent/malformed/inconsistent or parsed-vs-declared count mismatch; duplicate row ID or duplicate semantic row signature. Duplicate-anchor metrics alone are informational; they do not fail a run.
- `FAIL`, exit 2: cluster or map path missing, map unreadable/invalidly encoded, or structurally malformed Markdown (for example, a data row with a different number of cells than its header). A recognized map with a valid inventory but no recognized fact table is an inventory count failure (exit 1), so header drift is not misclassified as a generic parse error.
- `RESULT PASS` is allowed with WARNs and exit 0. Any exit-1 failure must produce `RESULT FAIL` and exit 1. Map/cluster errors produce `RESULT ERROR` and exit 2. Never emit a passing result when a FAIL was collected.
