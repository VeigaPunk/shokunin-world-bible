## Findings and limits, severity-ranked

1. **INFO — no drift.** Across 166 pre-existing fixtures, exit codes, violation counts and stdout digests are all unchanged at the candidate; the only set delta is the one added C2 fixture directory. Nothing in the census shows harm to any axis.
2. **LOW / methodology — the receipt is invocation-path sensitive.** Five fixtures whose output embeds the argv path (`r5-missing-file`, `r62-missing`, `r67-claim-source-unavailable-{control,empty,whitespace}`) hash differently if the checker is invoked with an absolute path instead of B1's repo-relative form. My first pass did exactly that and produced 5 spurious "changed" rows; re-running under B1's exact form gave 0 changed. This is a property of the *receipt*, not a behavior change — but any future census must pin the invocation form, or diff these five by content. (The fixtures' paths at HEAD are irrelevant to whether the file is missing; the message is deterministic.)
3. **LOW / limit — the hash field has no discriminating power among clean fixtures.** All 33 clean rows share one stdout digest (`afe570fc…c07e`); per-fixture discrimination comes from the fixture identity plus exit/violation count, not the digest.
4. **INFO / limit — "134 intentional negative" is documentation corroborated, not semantically proven.** Evidence: each negative fixture is named or family-documented in the committed README, all exits are the expected diagnostic `1` (never a crash code), and stderr is empty across all 167 runs. This is *not* an independent semantic review of each fixture's design intent. All-zero exits would have been the wrong expectation; negative fixtures exiting 1 is the design.
5. **INFO / limit — census ≠ content review.** The sweep proves process-level behavior (exit/stdout/violations) per fixture. It does not validate the Kojiki cluster's source mapping, the R8/R9 documents, or anything semantic; those are other seats' and other receipts' evidence.
