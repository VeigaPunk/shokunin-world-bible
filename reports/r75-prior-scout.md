# Round 75 prior scout — exact repeated relation rows

## Scope and judgment

Prior-art and materiality review only. I read the Round 75 LOG claim, active checker, fixture README, and the requested r2/r7/r45 reports plus duplicate-member/ID precedents. No checker, fixture, README, or LOG edits were made. **Judgment: NO-GO for treating this as an established material coverage gain; GO only to a bounded matched probe if the parent wants evidence before deciding.** The code appears not to detect an exact repeated relation row, but absence of a diagnostic alone does not establish that repeating a row is an error or that reporting it is materially useful.

## Direct precedents and overlap

- **R2 directly anticipated this scope and left it open.** `reports/r2-rule-scout.md` says duplicate A→B rows do not supply the reverse B→A edge, but explicitly says duplicate-relation policy is undeclared and should not be added as a symmetry failure or generic deduplication rule. `reports/r2-fixture-scout.md` likewise says the r2 reciprocal pair does not test duplicate handling and warns against quietly adding that behavior. R2's alliance reciprocity rule is distinct from a same-direction exact-repeat detector; it cannot be counted as prior endorsement of the proposed rule. It does establish a useful boundary: repeats must never satisfy missing reverse direction.
- **R7 is about identifier ambiguity, not duplicate relation records.** `reports/r7-alliance-scout.md` and `reports/r7-axis-adjudicator.md` concern repeated `source_id` rows in `sources.json`, whether an ambiguous source ID qualifies a citation/witness, and local reference diagnostics. They preserve the source rows and avoid choosing a source by order. They do not establish that two equal relation rows are redundant, erroneous, or evidence of one source assertion. A repeated relation's `source_id` may itself be unique; row identity and citation-ID identity are separate questions.
- **R45's materiality objection is a caution, not a direct duplicate-record precedent.** `reports/r45-ontology-scout.md`, `r45-critic.md`, and `r45-axis-adjudicator.md` reject a faction-kind occupancy exemption because the same observable kind can encode distributed outposts or a singular focal location; a broad rule might suppress a genuine conflict. This is not relation semantics, but its method applies: do not infer semantic meaning from a structural label without a discriminating input contract. An exact tuple can reliably identify identical fields in this JSON array, but the schema has no occurrence/mention field to show whether identical repeated entries are accidental duplication or intentionally repeated representation.
- **Other duplicate policies are bounded to their own structures.** R8 (see `reports/r8-critic.md` and README Round 8) treats repeated dependency-list IDs as input-list integrity, while warning that duplicate members may repeat downstream unknown/inversion diagnostics and are not proof of causal/lore error. R9/R12/R24 handle duplicate IDs that make a particular target/identity ambiguous; they do not deduplicate assertions. R59 is the closest parser precedent: `reports/r59-prior-scout.md` explicitly distinguishes duplicate JSON object member names from duplicate array-row IDs, and `r59-axis-adjudicator.md` admits strict member rejection only after a matched raw `place_id` order pair changed a consequential checker result (violation versus CLEAN), alongside controls. That is substantially stronger materiality evidence than currently present for repeated relation rows.

## Current checker / README boundary

The active `check_bible.py` relation pass checks relation endpoint membership/ambiguity and source-ID resolution; it has no exact tuple repetition check. Relation schema fields are `from`, `to`, `type`, and `source_id`; relation rows have no occurrence identity. README's relation convention (r2) requires sourced reverse `allied_with` rows for eligible distinct faction pairs, and expressly says it is a chosen data convention rather than universal alliance truth. README's source boundary says source IDs refer to fictional records and do not establish source-text support. Thus an exact `(from,to,type,source_id)` repeat is an observable structural equality in one input array. It does **not** establish duplicate source prose, a single underlying mention, an invalid or false relation, or a unique canon relationship. Conversely, two same-direction rows with different source IDs are not exact duplicates and may represent separately cited assertions; reverse direction remains a different tuple.

## Materiality and risks

The proposed later-row index diagnostic is plausibly actionable for cleaning redundant input and is narrower than a generic relation deduplicator. But unlike r59, no inspected prior report demonstrates that ordering identical relation rows changes a consequential checker decision or masks a validation error. Currently both would simply be traversed and independently validate; no semantic inference is made from multiplicity. The case for a warning therefore rests on an unstated array uniqueness convention. R2 expressly declined to supply that convention. Same-source exact repeats might be accidental copies, but they might also intentionally encode repeated mentions that this schema cannot distinguish. Flagging the second could incorrectly imply the repeated assertion is disposable; silently removing or collapsing it would be worse and is not warranted.

Before implementation/admission, seek an explicit input-level rationale and a matched probe: exact repeated directed tuple, same endpoints/type with distinct source IDs, reverse edge, and ordinary unique control. Show the new finding is confined to the exact repeated row and later index; show reverse-edge logic is unaffected, distinct citations remain represented, and no source/canon conclusion is implied. If there is no project convention or user need for array uniqueness, the reviewer may reasonably find the warning non-material and reject it. If pursued, phrase it as structural input repetition only, never as an adjudication of relation truth.

## Explicit non-claims and limitations

This scout did not run CLI probes or inspect every fixture/report; it relies on the current checker source and cited prior reports, and makes no claim about external JSON conventions. Structural duplicate means only equality of the four relation fields in one array. It does not resolve source truth, fictional canon, rights or licensing, or gameplay/mechanics. R2/R7/R45 are precedents with distinct scopes, not proof of the proposed rule's correctness. Existing fixtures having no exact repeated tuple (as LOG reports) establishes no real matched positive/negative example and does not measure materiality.
