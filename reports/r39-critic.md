# Round 39 critic — novelty falsification and collateral output

## Novelty challenge

The proposed case is **not a new checker branch or rule**. Round 7 explicitly mapped the contradiction-ledger unknown-source path: its then-current check used membership after an exact-one event lookup and emitted “no resolvable source_id” (`.shokunin/lore/reports/r7-source-scout.md:54-62`). More decisively, the independent r7 reviewer ran a temporary ledger probe with a uniquely resolved event whose `source_id` was absent, observed the ledger-side unknown diagnostic, and distinguished it from ambiguity (`.shokunin/lore/reports/r7-reviewer.md:34-40, 44-49`). The r7 test scout also identifies this check as existing ledger behavior (`.shokunin/lore/reports/r7-test-scout.md:...`—see report's ledger discussion). Thus an unknown-source-at-ledger-endpoint fixture would make the old temporary probe durable/replayable, but would repeat already-observed behavior; it cannot support a coverage-improved verdict under the declared novelty standard.

Round 38 is also direct near-prior-art: it traced this exact post-event source-status branch and explicitly documented unknown as the alternate case to ambiguous (`.shokunin/lore/reports/r38-source-scout.md:5-6, 25`; `.shokunin/lore/reports/r38-critic.md`, “Novelty challenge”). Round 38's actual duplicated-source probe is ambiguous, not unknown, but its ledger branch discussion already anticipates the unknown diagnostic. The r39 LOG declaration itself says scouts must search temporary as well as committed probes (`.shokunin/lore/LOG.md`, Round 39 declaration). The historical reports do **not** prove the exact unknown-source probe was already executed. They do show the branch and expected diagnostic were known; a “never documented” claim would be overconfident. Whether durable replay of this known edge case counts as a coverage gain is an adjudication question, not a novelty fact.

## Checker path and proposed collateral

Current checker counts schema-valid source rows and returns unknown/unique/ambiguous (`.shokunin/lore/corpus/fixtures/check_bible.py:53-66`). For each ledger side, it requires exactly one event (`:77-95`), then checks that event's source status: unknown yields a ledger-side `event '<id>' has no resolvable source_id` at `:96-100`; it does not call the ordinary `source()` diagnostic for this case. The timeline loop independently reports its own unknown citation (`:229-242`; verify current line positions when replaying, as later edits can shift them).

A one-field mutation of the Sella timeline event to `missing-sella-note` should therefore produce at least two findings: the ledger-side unknown-source result for `contradictions[0].claim_b`, and the timeline-local `timeline[3].source_id: unknown in-world source ...`. The event ID and both ledger pointers stay uniquely resolved; `claim_a` remains unaffected. This is expected duplicate reporting of one missing ID at two use-sites, not evidence that the event is false or that the ledger conflict is resolved. It must not be described as disproving Sella's report, establishing Tarin's account, verifying either excerpt, or determining canon. `sources.json` stores fictional metadata, not the cited prose; `r35-bell7-conflict/contradictions.json:1-14` labels the ledger's apparent conflict unresolved and non-canon.

## Falsifiable check

Before implementation, inspect any retained temporary probe artifacts and the full historical record. Existing reports establish branch knowledge but not an exact executed unknown-source ledger probe. If one is recovered, it falsifies “not tested anywhere”; absent that, describe the proposal narrowly as making a known branch durably replayable, not as new checker behavior. If nevertheless measuring an r39 clone, compare a clean r35 control against a copy changing only `timeline[3].source_id` to `missing-sella-note`; capture full stdout, stderr, exit, and all deltas. The control should exit 0; the variant should retain unique event IDs and emit both use-site diagnostics above, with no unrelated output changes. This validates repeatability/output collateral only. Because r7 already exercised the same unknown ledger-source behavior, even a successful replay does **not** establish new coverage; classify coverage unchanged and reject the round's candidate unless independently reframed to a genuinely untested behavior.
