## Risks and limits

- Inventory drift or an unpinned checker can make a nominal “86/429” comparison misleading. Use the exact baseline commits and publish sorted manifests; explain any count mismatch rather than silently changing denominator.
- Comparing only exit codes, saved stdout, or normalized text can miss changes. Compare each old fixture's exact stdout bytes, stderr bytes, and status.
- An r33-derived fixture could inadvertently alter inherited data. Require all 429 pre-existing JSON paths unchanged, and separately inspect inherited r33 rows; if the intended same-bell phrase requires a Tarin excerpt edit, confine it to the new fixture and document it as a new file, not a mutation of r33.
- “Same named bell” is shared wording in two newly authored fictional accounts, not independent clock synchronization or proof that events were simultaneous. A shared local tick is fixture metadata, not a temporal inference. Check that wording does not imply more precision than the accounts provide.
- A valid ledger pair merely resolves event-field references. It does not establish semantic incompatibility, source credibility, or which report is true. Keep both reports and the contradiction unresolved; do not infer a canon winner or any Blue Seal/carbon/route-strip association, envelope contents, ownership, recipient, motive, rights, or AI-training permission.

A checker exit 0 or syntactically valid `why` cannot prove this semantic reading.
