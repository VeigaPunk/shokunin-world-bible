# Round 69 critic — malformed-side same-reference finding

## Critic verdict

**NO-GO for declaring a material calibration gain on the present evidence.** The proposed gate plausibly removes a misleading comparison when neither side identifies a usable reference, especially when keys are missing or event IDs are malformed. But the opposite case is already concrete: the committed `r62-malformed-side` fixture has the same valid, nonempty `event_id` on both sides and the same invalid `field` (`"bogus"`), and the active checker emits the same-reference finding alongside both field errors. That finding can still be an independent repair hint: after correcting the invalid fields, the author must ensure the two references differ. The round declaration proposes suppressing it because the fields are not yet valid. No matched evidence establishes that this hint is useless or that its removal improves calibration enough to outweigh losing it.

This is not a claim that every same-reference result for malformed input is useful. In particular, two absent `event_id`/`field` values compare equal in Python and produce a finding without identifying any reference; likewise equal malformed event IDs are not usable pointers. The report supports a narrower distinction than “all malformed sides”: equality of a structurally valid event ID can retain repair value even if the field is malformed.

## Falsification of the claimed materiality

A duplicate-reference finding need not certify a valid reference to be useful as an input-ledger repair hint. In the concrete r62 fixture, the shared event ID is well-formed; only the fields are malformed. If an editor changes both `bogus` values to the same allowed field, the same-reference defect remains. The existing extra line can warn against that incomplete repair and direct the editor to make one side point elsewhere. Suppressing it until both fields become valid may defer feedback to a later run. Thus “the pair is malformed” does not entail “the equality finding has no actionable value.” This attacks the central unsupported materiality premise; it does not establish that the warning is always preferable.

The probe needed to settle the tradeoff should hold all other bytes fixed and include at minimum: (1) both sides missing both keys; (2) same malformed event IDs; (3) same valid event ID with both fields invalid (the committed r62 case); (4) one malformed field and one valid field with equal raw values where possible; (5) valid same pair; and (6) valid different pairs. Capture full raw CLI outputs and ask an independent user/editor to repair each input without hints, recording whether retaining the line helps, misleads, or changes the repair. A simple changed-output fixture alone demonstrates gating behavior, not a material calibration benefit. The proposed matched controls do not explicitly require a malformed case with a valid shared event ID and compare repair utility, so the existing r62 case must not be treated as automatically proving the proposed removal is harmless.

A possible narrower policy worth testing is to retain a same-reference finding when the event IDs are the same nonempty string and the raw fields are equal, while suppressing equality of missing/unusable IDs (or other pairs with no usable reference). That is a critic alternative, not an implementation recommendation or verified solution. Whether an invalid field pair should trigger depends on a stated ledger contract: if the intent is only to prohibit duplicate *valid* assertion references, the current finding may be overbroad; if the intent includes duplicate attempted pointers as repair guidance, it may be valuable. Current documentation/evidence does not resolve that intent.
