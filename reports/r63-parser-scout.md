# R63 parser-scout — independent calibration assessment

## Verdict: conditional GO, narrowly

There is a real parser-boundary gap, distinct from r59 duplicate-member handling: Python 3.11 `json.loads` accepts the non-standard constants `NaN`, `Infinity`, and `-Infinity` by default. This can bypass all current schema checks when placed in an ignored field. In an out-of-repository copy of `consistent/`, I added `"extra": NaN` to the first source row (`sources.json`); `check_bible.py` exited 0 with `CLEAN: schema, citations, relations, timeline; 0 violations`. The file/line is `.shokunin/lore/corpus/fixtures/check_bible.py:45` (decoder call); parser hook precedents are lines 16–23. Probe was under `/tmp`, not a corpus edit.

Nested and typed controls: Python decodes all three constants even in nested JSON (`json.loads('[NaN]') -> [nan]`, `{"x": NaN} -> {'x': nan}`). Replacing the first `timeline[0].tick` with each constant yielded required-int schema findings (as expected, because `type(nan/inf) is int` is false); valid integer `1` retained CLEAN. A finite decimal `1.5` in the same typed int slot also receives the same required-int finding. Thus the material case is not typed numeric rejection; it is non-finite constants in otherwise ignored/extension members, silently accepted by the generic parser. These observed outcomes distinguish current behavior from a hypothetical future hook.

Prior art and boundaries: r5 measured missing/invalid/wrong-top-level/row-shape/unknown-citation outcomes, not non-standard numeric tokens (LOG Round 5 closure). R59 (LOG Round 59 closure) rejects duplicate object members recursively; that does not imply a complete strict-JSON parser. Python's `parse_constant` callback is the narrow documented mechanism to reject exactly these spellings; retain existing `object_pairs_hook`, raise a parse-level error, and avoid inventing nested row locations. Report file plus token, and preserve ordinary finite JSON numbers. The policy is a newly explicit strict-input rule, not evidence that a particular world fact is false.

Materiality caveat: r59 already established that malformed JSON input is rejected, but its exercised syntax error does not establish that Python's decoder accepts these three non-standard constants. On the evidence above, rejecting them closes a demonstrated route to a CLEAN result for malformed input with no schema path; calibration gain is plausible and specific. Recommend GO only if the executor tests all three spellings at root/nested/ignored and typed locations, preserves finite integer/decimal behavior and duplicate-member rejection, and documents whole-file unload cascades. Since parse_constant throws during whole-file decode, dependent table checks may produce cascades (notably entity/source/timeline references); retain direct diagnostic, do not misstate cascades as absent entities/sources/events.
