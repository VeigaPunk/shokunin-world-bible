## Proposed raw behavior versus current

**Current:** accept syntactically valid duplicate-member objects; `json.loads` collapses each repeated key to its final value before required-field/type and semantic checks. The checker may therefore validate a row whose earlier raw value differs, or decisions can vary if final value/order changes. The duplicate `place_id` probes above both happened to be clean; no consequence is established by them.

**Proposed (not implemented):** detect repeated object member names while parsing and return a deterministic per-file duplicate-member diagnostic, rejecting the affected input rather than selecting a value. If a parser hook naturally sees nested objects (`claims`, `claim_a`, `claim_b`), scope/location should be stated as a raw repeated-member finding, not as duplicate row IDs. Avoid subsequent semantic findings dependent on arbitrarily choosing a value. Preserve normal unique-key output and existing malformed JSON/load behavior. This proposed contract is not established by the inspected r5 matrix or current README.

Duplicate JSON object member names are not repeated table rows or duplicate `id` values. They are distinct input conditions and must not be reported with `index()`'s `duplicate <section> id` language.

## Calibration judgment

**Material CALIBRATION: NO-GO on the evidence currently available; conditional candidate only.** The uncertainty is real (last-wins decoding), but materiality is not demonstrated by the two measured valid-value cases: both returned CLEAN. The r5 precedent is not a specification that duplicate names must be rejected, and a global rejection hook could flag nested names beyond the proposed required field. Do not dispatch a checker change from this scout alone. A GO would require an independently reproduced, schema-valid pair whose raw duplicate order changes a materially misleading checker decision, plus evidence that deterministic ambiguity rejection is less misleading and does not create disproportionate cascade/noise; verify nested-key policy, unique-key exact output, every old raw tuple, and old JSON bytes. Without that evidence, no-go is calibrated, not proof the input is safe or intended.

**Falsifier for this NO-GO:** an independently rerun paired duplicate-key input demonstrates consequential last-wins decision variance in a relevant checker rule; narrowly scoped duplicate-member rejection prevents that variance, emits a stable local diagnostic without arbitrary-value semantic cascades, and preserves unique-key cases and prior raw outputs/bytes. If so, reconsider material calibration GO. Conversely, if the format explicitly permits/defines last-wins or the pair produces no consequential distinction, that falsifies the case for rejection.

## Risks / boundaries

- Rejecting all repeated keys might be an unsupported tightening of the input format; a parser-wide hook may also reject duplicate names nested in free-form claim records. Be explicit about location granularity and avoid claiming one offending field when parser evidence only supplies a path.
- Retaining last-wins risks order-dependent or masked validation, but the actual probe did not establish a material outcome. Do not overstate it.
- A duplicate-member diagnostic means only that one raw JSON object repeats a key under the selected parser policy. It does not establish which value a fictional author intended, any actual fictional location/source/event, source authenticity or support, story truth, canon, rights, license, or permission.
