# Round 75 schema scout — relation-row multiplicity

## Scope and evidence

Read the r75 declaration in `.shokunin/lore/LOG.md`, active `corpus/fixtures/check_bible.py`, fixture README, and relevant predecessor reports (especially r2 schema, r4 name/reviewer, r7 alliance/reviewer, r24/r45 relation precedent, and r74 schema boundary). This is a schema/representation assessment only; I made no checker or fixture changes and did not run candidate probes.

The active relation row has exactly four required nonempty strings: `from`, `to`, `type`, `source_id` (`check_bible.py`, `FIELDS['relations']`). The checker retains every well-shaped relation row, validates endpoint ID membership/ambiguity when entities are available, and checks source-ID resolution. It neither constructs a relation identity index nor diagnoses exact repeated tuples. The README says relations cite in-world fictional records and repeatedly cautions that citation-ID resolution is not source-text support or canon verification. LOG r75 reports its repository inventory found no exact repeated `(from,to,type,source_id)` tuple among 132 shipped fixtures; the one clean relation is `mira -> seal`, `carries`, `courier-log`.

Existing adjacent behavior is not an exact duplicate policy: r2 added a reciprocal `allied_with` convention between faction endpoints, requiring an independently resolvable reverse record, and says this is a chosen convention rather than universal canon symmetry. R7 clarifies duplicate source IDs make a citation ambiguous, not qualifying evidence. R24 addresses ambiguous endpoint entity IDs. Neither determines whether identical directed relation rows are accidental duplicates. R4's exact-name detector was rejected because distinct entities may be homonyms; it is a caution against treating representation equality as semantic identity, not a direct relation-row precedent.

## Can the same tuple encode independent claims?

**Not as separately identifiable claims under the current relation schema.** Two rows with identical four fields are byte/value-equivalent assertions: both name the same directed endpoints, predicate, and source ID. There is no relation-row ID, claim text, quotation/passage locator, time/scope, attribution, or multiplicity rationale by which a consumer or checker could distinguish two independent attestations. The checker cannot tell whether the second row is an accidental repeated input row, duplicated serialization, or an intended second mention.

That representational limit does **not** establish that independent underlying claims cannot exist. One fictional source record may in principle contain multiple passages or repeated attestations; distinct witnesses may also independently support the same proposition. `source_id` points only to a source record, not a passage or a particular assertion. Therefore an exact duplicate tuple cannot encode that independence, while the tuple alone cannot rule it out. To represent separately addressable claims, the schema would need an explicit identity/claim or evidence-location model; adding such a model is outside this round's declared narrow move.

By contrast, changing `source_id` preserves a distinct citation reference in the available representation, and reversing `from`/`to` changes direction. The current shape can therefore distinguish those rows structurally, but cannot establish source independence or semantic correctness. The directed tuple comparison should remain exact and must not normalize strings or silently collapse reverse edges/types.

## Structural duplicate versus truth, canon, rights, mechanics

An exact tuple duplicate is objectively detectable as repeated input structure. A later-row-index warning could tell an editor which repeated row to inspect, but the checker has no basis to label it a false claim, redundant evidence, false relationship, canon inconsistency, or proof of one unique relationship. Conversely, preserving duplicate rows does not show there are multiple independent claims. Source IDs and clean checker output establish only structural references, not cited prose, authenticity, rights, or whether a game mechanic/lore rule is true. No source text or rights evidence is inspected here.

## Risks, limits, verdict

A narrow repeated-record diagnostic would add structural coverage not presently implemented, and its declared boundary (identical directed tuple only) is testable. But material calibration is unresolved: the existing schema cannot represent the distinction the diagnostic would use to separate accidental duplication from legitimate repeated independent claims. Since the proposal makes every exact repeated tuple nonzero/violating without an exemption or evidence pointer, it risks rejecting a legitimate intended representation; the absence of an identity field is not evidence that multiple mentions are invalid. A matched distinct-source and reverse-edge control can establish scope isolation, but cannot settle this ambiguity. Existing 132 clean fixtures and no observed exact repeat likewise do not establish the semantic rule.

**GO** only for a future explicit schema convention that repeated identical relation rows are structurally invalid regardless of underlying independent mentions, or for a representation that gives independent claims distinct identities/evidence locations and an operationally clear duplicate key. **NO-GO for admitting the proposed checker diagnostic on current evidence.** Keep this as a structural-duplicate candidate, not a canon/source-truth finding; no checker or corpus edit is recommended. This scout did not independently replay all 132 fixtures, authenticate source material, test production consumers, or establish rights/mechanics/canon facts.
