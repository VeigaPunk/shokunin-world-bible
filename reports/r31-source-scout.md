## Current source-status and relation path

- Source records are indexed and duplicate IDs are reported at `check_bible.py:45-56`. The index is last-record-wins (`:47-51`), but a separate `source_id_counts` retains multiplicities (`:53-56`).
- `source_status` classifies count 0/1/>1 as unknown/unique/ambiguous (`:64-66`). `source()` emits a location-specific unknown or ambiguous citation diagnostic (`:68-74`).
- Every relation row checks endpoints and then calls `source(row['source_id'], location + '.source_id')` (`:123-130`), without restricting by relation type. Therefore a duplicate ID on a `carries` relation should yield the relation-local ambiguous-source finding; this is an existing general citation check, not a new rule. Relation schema is declared at `:11`.
- The reciprocal alliance witness loop separately selects `allied_with` rows (`:210-213`) and counts a reverse edge only if its source status is unique (`:219-224`). Ambiguous source citations on reverse alliances therefore also cause the outer relation to lack a *sourced* reciprocal (`:225-226`), a collateral diagnostic independent of the generic relation citation finding. This explains why r7's reverse-alliance probe is not a clean generic-relation-only example.

## Collateral paths and risks

- Contradiction ledger source resolution uses `source_status` on the event source (`:92-100`): unknown source gives the ledger-specific “no resolvable source_id” finding; ambiguous source additionally goes through `source()` at the ledger side location. An ambiguous event source can thus produce both the ledger-specific finding and an ambiguous citation finding. Do not mistake these for consequences of the relation probe; the controlled pair should leave timeline/contradiction inputs unchanged.
- Item provenance also calls `source()` (`:186-194`). Unknown IDs invalidate the record; ambiguous IDs set `chain_has_ambiguous_source`, but remain structurally valid (`:190-198`). Subsequent tick/holder chain diagnostics are explicitly prefixed “input-structural finding, not sourced-canon” once ambiguity was seen (`:199-206`). This is an intentional qualification, not suppression of the chain checks.
- The raw duplicate diagnostic remains in addition to each ambiguous citation; duplicating `courier-log` can consequently flag all other unchanged claims, first appearances, timeline citations, provenance citations, and this relation that cite it. The Round 31 LOG explicitly requires inventory of the full legitimate delta, not a relation-only claim (`LOG.md:480-481`).
- Because the ID index retains the last row (`:47-51`), callers must rely on counts/status rather than interpreting the selected record as uniquely authoritative. Current relation checker only establishes source-ID uniqueness, not that an in-world document supports the relation or establishes canon truth.
