# Round 4 critic — name-collision coverage

## Result

I could not establish that equal `entities[].name` values are inherently inconsistent. The proposed exact duplicate-name rule is mechanically testable, but the current evidence does not establish name uniqueness as a canon or schema invariant. It can therefore increase false positives unless it is explicitly scoped as a fixture/editorial convention. Do not describe it as detection of a canon error.

## Falsification probes and observed behavior

- **Duplicate IDs are already a separate invalidity.** In `.shokunin/lore/corpus/fixtures/check_bible.py`, `index('entities')` reports a duplicate entity ID, then overwrites the earlier row in the index. Both valid entity rows remain in `data['entities']`. A future name pass over raw rows could emit misleading duplicate-name output for records that are not distinct entities; a pass over the index could silently lose one participant. Recommendation: only evaluate name pairs after checking that both IDs are distinct and each occurs exactly once; preserve the existing duplicate-ID diagnostic independently.
- **Malformed names are not normalized by the current schema.** The entity schema requires `name` to be a nonempty `str` with `.strip()`, but stores and compares the original value. Thus `"Mira"` and `" Mira "` both pass validation and are unequal under an exact comparison. The current fixtures in `.shokunin/lore/corpus/fixtures/consistent/entities.json` use trimmed names, but the checker does not enforce that convention. A check for equal exact names will miss whitespace variants; trimming for comparison instead changes the proposed exact/case-sensitive rule and can invent a collision. Recommendation: do not silently normalize; either make canonical whitespace a separately documented schema constraint (and test malformed names) or state that whitespace variants are outside this rule.
- **Legitimate homonyms remain plausible.** The entity kinds are `character`, `place`, `faction`, and `item` (`KINDS` in the checker). There is no kind-aware identity or uniqueness constraint on names. Two distinct characters can legitimately share a personal name; same strings across different kinds are even less evidence of collision. The four ordinary example entities in `consistent/entities.json` happen to have distinct names, which is not evidence that duplicates are invalid. Recommendation: if keeping a hard violation, constrain it to the data domain where the convention is intended (at minimum same kind), and label this as a local convention rather than a universal lore consistency rule. Better still, report duplicate display names as a review warning unless a bible explicitly opts into uniqueness.
- **Exact equality is a narrow detector.** It will not catch case variants (`Mira` / `mira`), aliases, transliteration, punctuation or Unicode normalization variants. That is consistent with the round-4 declared boundary, but coverage claims must remain limited to byte-for-byte/case-sensitive string equality; do not imply broad name-collision coverage.

## Separate recommendations

1. **Scope/semantics:** Define whether duplicate display names are errors, warnings, or merely candidates, and which entities are compared (all kinds vs same kind). State that this is an editorial convention, not a fact about canon. Without an explicit uniqueness premise, recommend warning-only.
2. **ID interaction:** Exclude any row whose ID is duplicated from the pairwise name rule; retain the duplicate-ID error. Ensure the diagnostic identifies both stable entity locations and IDs.
3. **Input shape:** Decide separately whether leading/trailing whitespace is invalid. Do not normalize names opportunistically in the new check.
4. **Evidence:** Include a positive exact-match pair with different unique IDs and a clean negative containing distinct IDs with the same legitimate name (preferably same kind), plus a same-string cross-kind case if the rule is kind-scoped. Include duplicate-ID/same-name and whitespace-variant probes so those boundaries are observable. Cite the local assumption in the fixture documentation.
5. **Claim calibration:** If only the exact duplicate pair is covered, call the result an exact-string duplicate-name check, not general name-collision detection. Keep aliases, case folding, transliteration and semantic identity explicitly out of scope.

Observed sources: `.shokunin/lore/corpus/fixtures/check_bible.py` (`FIELDS`, `index`, entity validation); `.shokunin/lore/corpus/fixtures/consistent/entities.json`; `.shokunin/lore/corpus/fixtures/README.md` (current local fixture conventions). No canon source or existing fixture establishes name uniqueness.
