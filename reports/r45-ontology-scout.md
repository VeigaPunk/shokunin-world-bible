# Round 45 ontology scout — faction occupancy

## Decision

**NO-GO on changing occupancy based on the current evidence.** The proposed two-outpost report can establish what an invented source *says*, conditional on its authored wording; it does not by itself establish that this schema treats faction subjects as distributed collectives or that a faction actor denotes multiple members/locations. The README's character-specific sentence documents an occupancy rule for characters. It is not an explicit exclusivity clause (“only characters may be actors”) nor an exception (“factions may occupy multiple places”). The generic `entity_id` field means a faction is admissible as a subject by kind/reference, but does not define occupancy semantics for it.

## Path:line evidence

- `.shokunin/lore/corpus/fixtures/check_bible.py:7-13` enumerates `character`, `place`, `faction`, and `item`; `timeline.entity_id` is required only to be a string. No event-subject kind or faction-distribution contract is encoded.
- `.shokunin/lore/corpus/fixtures/check_bible.py:228-252` resolves actor ambiguity, then compares occupancy for every actor ID with exactly one admitted entity, a uniquely resolved place, and nonnegative tick. The key is `(entity_id, tick)` and a different `place_id` yields `double-booked` (`:245-252`). There is no kind-specific exclusion. Thus a uniquely identified faction subject will enter the same occupancy calculation as a character if the controlled input reaches this branch; source text does not alter that structural algorithm.
- `.shokunin/lore/corpus/fixtures/README.md:29-34` says “A character cannot occupy different places at the same tick” and allows same-place simultaneous records. It does not state that all entity kinds have one location, or that factions represent distributed outposts. Nor does it say only characters are valid event subjects. Extending the sentence to factions, or inferring the opposite exception, would add policy not written there.
- `.shokunin/lore/corpus/fixtures/README.md:18-27` explicitly distinguishes faction entities in a relation rule: only `allied_with` between distinct factions triggers reciprocity. This is a relation convention, not a timeline/faction-mobility or occupancy definition.
- `.shokunin/lore/corpus/fixtures/README.md:243-265` describes r12's unique/ambiguous actor occupancy comparison using `mira`; it tests ID certainty, not kind semantics. `.shokunin/lore/corpus/fixtures/README.md:443-468` says r21's occupancy guards require a unique actor/place and nonnegative tick; its cases keep character `mira` and vary malformed dependencies/place eligibility, not faction actors.
- `.shokunin/lore/LOG.md:750-752` records r44's rejection of the inverse blanket inference: generic actor field plus character-specific README prose did not justify rejecting noncharacters. R44 does not prove factions are spatially distributed; it leaves that question open. `.shokunin/lore/LOG.md:755-756` correctly labels the r45 faction-outpost idea a hypothesis and makes source/canon limitations explicit.

## Risks and precedent

The proposed excerpt can support a *fictional authored assertion* that the faction kept separate outposts at the two named places during a named local watch, if a reviewer maps the exact clauses to both events. It cannot authenticate the text, prove the world fact, establish that `entity_id` means the faction's entire membership rather than a singular representative/office, or establish that distinct event locations represent simultaneous presence by one indivisible actor. Conversely, generic schema acceptance does not prove faction occupancy should be exempt.

A blanket “factions may be at multiple places” exception risks suppressing a real same-faction conflict when records mean a singular headquarters, delegate, or faction-level location. A “faction outposts” prose label does not establish a general faction ontology; an exception limited to one hand-authored report might simply encode the desired answer into the fixture. The character control is useful regression evidence, but cannot validate the faction exception's semantic premise. Existing r12/r21 evidence is not a precedent for the faction case; it addresses identity certainty and independent occupancy checks.

## Falsifiable gate

**Current candidate: NO-GO / no checker or fixture change.** Before implementation, the project needs an explicit, scoped occupancy convention that distinguishes a collective faction with distributed outposts from a singular actor/location assertion, and defines whether `timeline.entity_id` names the faction collectively or an individual representative. Then test a minimal source-cited faction case and matched character conflict: the faction pair should avoid only the intended false same-actor conclusion under that documented meaning; the character pair must still report `double-booked`. Include a faction case whose source asserts one singular location to test that the exception does not suppress a supported conflict. If all factions are meant to have one timeline location, or the event subject is a singular envoy/representative, retain the current finding. If no ontology rule can discriminate these meanings independently of the desired outcome, no-go remains.

A clean checker run, unique source IDs, and a manually authored excerpt establish neither source authenticity nor factual/canon truth. No checker, fixture, README, LOG, or SCORECARD change is recommended by this scout.
