# Round 6 schema scout — required files, malformed records, duplicate IDs

Scope: map current checker behavior and the schema consequences for explicit item-transfer records. This is a read-only scout, not an implementation or a claim about canon.

## Observed in the repository

- `check_bible.py` declares five tables in `FIELDS` (`sources`, `entities`, `relations`, `timeline`, `contradictions`) and loads **each table as required** by opening `<section>.json` in the loop (`.shokunin/lore/corpus/fixtures/check_bible.py:8-15, 21-30`). A missing file is reported as `cannot load JSON`, then represented as an empty table; processing continues. A present non-array adds `expected array` and is also treated as empty (`:23-30`). Thus adding `transfers` to `FIELDS` would make `transfers.json` required in every bible, including the current examples, unless every fixture is updated. The existing clean example has exactly those five files; its timeline currently models Mira's place occupancy, not item custody (`corpus/fixtures/consistent/timeline.json`; `corpus/fixtures/consistent/entities.json`, item `seal`).
- A row must be an object and must have every declared field with the exact Python type (notably `type(value) is expected`); invalid rows are excluded from `data[section]` while diagnostics accumulate (`check_bible.py:31-43`). This is validation of required fields, not a closed-object schema: extra keys are not rejected. Therefore putting explicit transfer records as extra fields on existing rows would not currently validate their shape or required citations.
- `index(section)` reports duplicate IDs but still overwrites the earlier row in its returned dictionary with the later row (`check_bible.py:45-56`). It is called for `sources`, `entities`, `timeline`, and `contradictions`; relation rows have no `id` field in `FIELDS` and no index. Timeline ID counts are separately retained (`:57-59`). A duplicate timeline ID consequently produces a duplicate-ID diagnostic, while lookups through `events[id]` resolve to the last valid row. The contradiction ledger explicitly avoids silently relying on that: its event reference requires exactly one timeline record, otherwise it reports `expected exactly one timeline event` and skips the lookup (`:65-86`). The timeline dependency rule, in contrast, checks membership in `events` and then uses the last indexed row's tick (`:151-155`).
- Invalid required fields keep a row out of `data`, so such a row cannot participate in indexing or event-ID counts (`check_bible.py:37-43, 45-59`). The loader is not fail-fast: errors from missing/malformed input can coexist with downstream diagnostics on other tables. Round-5 knowledge explicitly warns that removing a referenced table can cascade into dangling-reference messages and limits its low-cascade observations (`corpus/knowledge/2026-10-12-malformed-error-patterns.md`, final paragraph).
- Source checks establish only that a `source_id` resolves in `sources` (`check_bible.py:61-63`; entity/relation/timeline calls at `:93-108, 132-140`). Existing documentation says source citations are in-world records but checker does not test source support or truth (`corpus/fixtures/README.md`, source/citation and Round 3 sections). A transfer's source pointer could be structurally checked, not semantically substantiated.

## Recommendations for transfer schema (not current behavior)

1. **Do not make provenance mandatory merely by adding a required top-level table.** The mission requires unrelated/legacy bibles with no transfer data not to hard-fail. Prefer an optional transfer representation (or an explicitly optional field/section with a documented absence meaning); if an optional file is introduced, the loader must distinguish “absent means no provenance asserted” from malformed/present-but-invalid. Otherwise document/update all bibles and accept that absence is an input error, which conflicts with the round claim.
2. **Give each transfer a stable unique ID and reject ambiguous duplicate IDs for chain resolution.** A duplicate must not be resolved by `index()`'s last-row-wins behavior. In particular, if transfers are stored in a new section, simply adding it to `FIELDS` does not automatically check IDs: `index()` is explicitly called for selected tables only. Add an explicit uniqueness/count policy for transfer IDs and have chain references require exactly one matching record, analogous to the contradiction ledger's exact-one event guard. Never use array order or dictionary overwrite as a tie-breaker.
3. **Keep malformed transfer rows from becoming chain evidence.** Require structurally valid record fields before indexing/chain checks, then report local field/schema errors. Avoid follow-on “unknown predecessor/holder” noise caused solely by a malformed row where practical; preserve the existing checker convention of reporting errors rather than repairing data. Test missing/invalid source, wrong row shape, and duplicate ID separately because the current loader continues after errors.
4. **Avoid overloading timeline IDs unless transfer records truly are timeline events.** Existing timeline records require `entity_id`, `place_id`, and location semantics, and their duplicate handling has the mixed behavior above. A transfer-shaped record should explicitly identify item, from-holder, to-holder, tick/order, and source; the schema should define whether its ID namespace is independent or shared with timeline events. If shared, enforce cross-record uniqueness; if independent, all references must be section-qualified or otherwise unambiguous.
5. **Keep “no provenance asserted” distinct from a broken chain and from conflicting cited records.** Missing optional transfer data should not imply a transfer or a chain break. A well-formed transfer with a missing/ambiguous prior holder can be diagnosed at that transfer; duplicate/conflicting evidence must be reported, never selected by input order. The current checker has no transfer-specific conflict semantics, so these remain design requirements, not observed outcomes.

## Minimal interaction matrix to test if implemented

| Input condition | Existing observed behavior / transfer-specific recommendation |
|---|---|
| No transfer section/data | Existing five required files load; clean example passes. For proposed transfers, absent optional provenance should remain non-error and should not assert custody. |
| Transfer file omitted, if declared required | Current loader pattern yields `cannot load JSON` and empty data; recommendation: do not make it required for this rule. |
| Transfer file malformed JSON or non-array | Existing loader records load/array violation and continues. Recommendation: fail that input locally, do not treat it as a valid empty provenance history. |
| Transfer row non-object / missing or wrongly typed required field | Current section mechanism reports row/field errors and excludes invalid row from later checks. Recommendation: invalid record is not chain evidence. |
| Duplicate transfer ID | Current generic `index()` reports duplicate but leaves last row in lookup; no automatic uniqueness check for unindexed sections. Recommendation: do not resolve a chain through either duplicate; mark reference ambiguous and report. |
| Duplicate timeline event ID referenced by contradiction | Observed: duplicate table ID diagnostic plus `expected exactly one timeline event`; this is the concrete safe exact-one precedent. |
| Transfer source ID absent from sources | Existing `source()` membership check yields unknown in-world source; this does not verify source support. |

Evidence citations above refer to current `check_bible.py` line numbers and committed fixture/docs paths. Recommendations are design guidance only; no new checker behavior or fixtures were exercised in this scout.
