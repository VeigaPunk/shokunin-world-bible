# Round 59 simplifier — duplicate JSON member calibration

## Scope and evidence

No checker, fixture, README, LOG, or commit was changed. The checker reads each of five JSON tables with `json.loads(path.read_text(...))` at `.shokunin/lore/corpus/fixtures/check_bible.py:18-26`; it screens decoded rows afterward at `:31-43`. Python's default decoder collapses repeated object keys, retaining the last value. The checker therefore cannot validate the raw repeated-member condition after decoding. This is distinct from duplicate entity/source/event IDs across separate rows, which the checker counts and reports (for example `:45-62`).

Read-only probe: copied `consistent/` to `/tmp/r59-simplifier-...`, inserted a second `place_id` member into `timeline[1]` with first value `harbor`, second `tower`, then ran the ordinary repo-root CLI. It exited 0 and printed exactly `CLEAN: schema, citations, relations, timeline; 0 violations`. The decoded row was the ordinary `tower` row. Thus actual behavior silently accepts this duplicate and selects last-wins; swapping order would select harbor. This probe demonstrates parser behavior, not that either fictional location is true or that timeline occupancy is canonical.

Prior malformed-input precedent is limited: r5 documents missing file, invalid JSON, wrong top-level shape, non-object row, and invalid citation (`knowledge/2026-10-12-malformed-error-patterns.md`, table rows); none tests repeated object members. The r5 note explicitly says its cases are not exhaustive. Existing `cannot load JSON` handling (`check_bible.py:24-27`) catches JSON decode errors but duplicate keys are accepted JSON under Python's default decoder. Duplicate row-ID findings are not precedent for rejecting duplicate keys inside one object.

## Smallest proposal / go-no-go

**Conditional minimal change:** use `json.loads(..., object_pairs_hook=...)` to reject any object containing a repeated member name, preserving detection at the raw parse boundary. Raise a `ValueError` subclass (or another caught parse exception) with a stable duplicate-member diagnostic and map it to the existing per-file `cannot load JSON` path; do not return a partial dict and do not run semantic checks on that file's arbitrary last-wins row. A tiny hook can construct a dict while checking each object's ordered pairs. Since the hook applies recursively, it naturally rejects repeated keys in nested `claims` and `contradictions[*].claim_a/claim_b` objects too; report file-level rejection only, without claiming row indices the hook does not know. Existing invalid JSON and read errors should keep their current behavior. Do not treat duplicate row IDs as duplicate members, rewrite inputs, or infer story facts/canon/rights.

**Material calibration: GO, narrowly for rejecting raw duplicate-member ambiguity; implementation remains unbuilt and unverified.** The evidence is a concrete false-clean: an input with two incompatible `place_id` values produces CLEAN solely because decoder last-wins erases the first. Refusing the ambiguous input improves calibration of the checker's stated input validation; it does not adjudicate either value. Proposed diagnostics should avoid cascading semantic findings from an arbitrary duplicate value. Risks: input producers may intentionally rely on last-wins (no such convention was found in inspected r5 precedent); a global recursive hook may reject duplicates in nested free-form objects users previously supplied; file-level wording may be less specific than row-path diagnostics; error wording/count changes must be tested against all old outputs. If schema/format documentation establishes last-wins as intended, or a real required use depends on repeated members, this GO is falsified and change should be NO-GO. Unique-key controls must retain exact output and exit status; both swapped duplicate orders must reject without choosing a location; malformed duplicate with one wrong-typed value must not cascade into semantics.

This is calibration only: no coverage or depth gain claimed. No implication about actual story truth, canon, rights, source reliability, or which location is correct.
