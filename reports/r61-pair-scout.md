# Round 61 pair-scout — source-index availability controls

## Independent verdict: GO, narrowly for calibration (not implementation)

A matched probe on `consistent/` demonstrates a distinct source-index availability defect: a failed `sources.json` load is currently converted to zero source rows, so every source reference is reported “unknown” as if absence had been established. In a temporary matched probe, the unavailable source file yielded one direct load error plus 11 unknown-citation findings; a successfully loaded empty array yielded the same 11 unknown findings without the load error. This is material output calibration if a later executor can withhold only source-index-derived unknown/ambiguous/unique conclusions while retaining the load error and all independent checks. This report authorizes no code/fixture changes and is not evidence about source content or truth.

## Proposed distinction and falsifier

Proposed policy (not observed): distinguish a successfully parsed array from unavailable/nonarray/malformed source input. On unavailable input, keep the direct file/shape error; withhold only conclusions requiring source ID membership/cardinality (unknown, ambiguous, or unique-derived certainty), and mark such checks unassessable rather than clean. Do not suppress malformed citation-field/schema findings, timeline tick/dependency checks, ledger pointer/event-ID/field checks, entity/relation structure, or other work independent of source lookup. In particular, an event ledger message “has no resolvable source_id” should not be asserted solely because the source table failed to load. A loaded empty array remains available and supports ordinary unknown findings; loaded partial arrays resolve retained IDs and leave missing IDs unknown under existing table semantics; loaded duplicate IDs retain ambiguity findings. A successfully parsed array with malformed rows is still available over the checker’s admitted rows, consistent with r32; do not silently redefine that rule.

Falsifier: a matched candidate must show unavailable vs loaded-empty vs loaded-partial vs loaded-ambiguous behavior with the four non-source tables byte-identical. If unavailable still produces index-derived unknown/ambiguous conclusions, if loaded-empty/partial findings disappear, if loaded ambiguity is treated as unique, or if unrelated negative tick / unknown dependency / malformed ledger structure checks are lost, reject. Also reject if auditing all source-status callers requires broad suppression that obscures useful triage or changes loaded-table behavior. The direct loader diagnostic must remain. An alternative defensible contract could explicitly define unavailable as empty for diagnostic purposes, but absent such an explicit contract, the current output is misleading about what the unavailable index establishes.

## Boundary and harms

This only concerns membership/cardinality in this checker’s input source registry. It proves neither whether any source exists in-world nor what a cited file says, supports, establishes, or contradicts. No conclusion about narrative truth, canon, chronology, authenticity, ownership, copyright, license, or permission follows. Potential harms: suppressing the useful list of affected source references can make recovery/triage harder; overbroad suppression can hide source-independent errors or source findings for loaded valid rows; an ambiguous/unique gate may be necessary to alliance reciprocity and ledger logic, so careless guarding could create false confidence. Keep output explicit that lookup was unavailable and do not call the dataset CLEAN.
