# Round 84 prior-scout — duplicate event IDs and occupancy

## Scope

I read the Round 84 declaration in `.shokunin/lore/LOG.md` and the cited Round 9, 11–13, 16, 19, 37, 52, and 70 reports, along with the relevant fixture precedent identified there. This is a prior-art/materiality audit only. I did not edit or run the checker or fixtures. Round 84 concerns calibration: whether a duplicate timeline `id` should qualify or suppress a `double-booked` finding for rows that otherwise have a uniquely resolved actor, local tick, and distinct uniquely typed places.

## Closest precedent: Round 12 is analogous but not the same key

Rounds 12 and 13 withheld definite occupancy when the occupancy **actor key** had multiple matching entity rows (R12), or no matching entity row (R13). That changes the certainty of the predicate itself: the checker cannot establish that two rows name the same resolved actor. R16 similarly narrowed occupancy to rows with uniquely resolved place IDs of kind `place`; R19 required a nonnegative tick. Those rounds explicitly kept the local ambiguity/dangling/domain diagnostics and raw timeline rows, and did not claim the conflict was absent. Their precedent supports qualifying a finding when one of its actual comparison operands is unresolved or outside the rule's domain.

R84's duplicate is instead in the timeline event **label** (`id`). The proposed occupancy comparison uses the row's actor ID, tick, and place ID; it does not dereference event IDs. If actor and place are unique and both ticks are eligible, the two supplied rows still structurally assert the same actor/tick at different places, regardless of whether a separate event label is duplicated. Unlike R12's actor duplicate, duplicated event labels do not by themselves make the actor key ambiguous. Applying R12's suppression policy solely because a row's unrelated event label is duplicated would be a new and materially broader analogy, not an established precedent.

## Other named rounds and fixtures

- **R9:** Duplicate event IDs caused an order-dependent dependency inversion because dependency validation dereferenced the event ID through a last-wins index. R9 fixed that consumer by reporting an ambiguous dependency and skipping its tick comparison when the target ID was non-unique. This is directly relevant to consumers that use event IDs to select a row, but occupancy does not. R9 does not establish that all diagnostics on rows with duplicate IDs become indeterminate.
- **R37:** The duplicate-event fixture tests a contradiction-ledger endpoint. The ledger explicitly points to an event ID, so duplicate cardinality defeats exact-one endpoint resolution; the checker emits the duplicate-ID and endpoint-local error and does not select the last row. This is not an occupancy precedent: R37's adjudicator says generic duplicate-ID behavior was already covered by R9 and identifies the novel behavior as the ledger endpoint cardinality. The r37 duplicate row is a copy of Tarin's event, and the observed output has no double-booking finding. It therefore supplies no matched evidence that a duplicate label makes an otherwise eligible actor/tick/place comparison unsafe.
- **R11:** Entity-index ambiguity changed the timeline place-kind conclusion because the lookup used the last entity row; the fix reported ambiguity instead of selecting a kind. Again, this is an actual operand lookup, unlike an event label not read by occupancy.
- **R16/R19:** These distinguish resolved place eligibility and valid tick domain from unrelated warnings. Their narrow guards do not prove that every row carrying any other validation error must be excluded from occupancy. The Round 16 adjudicator also notes residual wrong-kind/ambiguous-place cases were not generalized away; R19 separately leaves raw-negative dependency policy untouched.
- **R52:** Its rejected proposal concerned ambiguous **source IDs**, not duplicate event IDs. The R52 adjudicator found source ambiguity does not invalidate the independent raw actor/place/tick collision and warned that qualifying/suppressing the collision could lose an actionable input-field finding. The source ID is not the occupancy key; this is a useful caution against broad propagation of an unrelated identity ambiguity. R52 did not test duplicate event IDs, so it is cautionary, not dispositive.
- **R70:** Its ledger same-reference comparison concerns pointer objects, not occupancy. R70's adjudicator rejected a plausible diagnostic suppression when the lost pair warning could prompt a useful first repair; raw output change and old-suite preservation did not establish material benefit. R70 does not answer R84, but its materiality standard applies: show a different safe editor action or demonstrated reader harm, not just a technically different output.

## Materiality assessment and recommendation

On the evidence in the named prior reports, the duplicate-ID warning and the occupancy warning are independently actionable: one says two admitted timeline rows reuse a label; the other says two supplied rows meet the checker’s actor/tick/place collision predicate. The event label can affect dependency and ledger-pointer consumers (R9/R37), but does not make the occupancy operands ambiguous. A duplicate-ID diagnostic already tells the editor to repair the label; suppressing the occupancy finding could additionally hide a distinct actor/place/tick issue. Conversely, the collision message must remain bounded to supplied input fields and not be described as proof of source support, event identity, a narrative contradiction, or canon.

**Prior-art disposition: NO-GO for suppressing or downgrading `double-booked` based only on duplicate event IDs, absent evidence of a material misreading or a concrete safer first repair.** The R84 matched distinct-ID control is useful to establish output contrast, but contrast alone is not gain. A candidate would need independent evidence that the duplicate event label makes the editor take an unsafe occupancy repair (or otherwise causes a material calibration error), and that withholding/qualifying the collision changes the safe first action without hiding an independently valid input-field finding. If such evidence is unavailable, retain the collision alongside the duplicate-ID finding. A mere extra ambiguity warning risks duplicating the global duplicate diagnostic without clarifying which occupancy operand is uncertain.
