# Round 69 regression scout — raw tuple inventory and pinned replay plan

## Scope and pin

The Round 69 declaration in `.shokunin/lore/LOG.md` (Round 69, lines 1212–1215) pins clean baseline `583f97e40f0c5d0bcd0c51be1a408e7d3005b9c6`. `git rev-parse HEAD` returned that exact commit. The active checker is `.shokunin/lore/corpus/fixtures/check_bible.py`; its current `claim_a`/`claim_b` equality test follows each side's structural/index checks and runs whenever both sides are dictionaries with equal `.get('event_id')` and `.get('field')` values (including absent/malformed values). The corpus was not modified for this report. This is an inventory of baseline behavior, not a candidate replay or an admission judgment.

## Existing raw fixture outcomes

I enumerated fixture directories directly from `.shokunin/lore/corpus/fixtures/` and invoked the checker from repository root for every directory using the same relative-path pattern, `python3 .shokunin/lore/corpus/fixtures/check_bible.py .shokhun/lore/corpus/fixtures/<case>` (the actual invocation used `.shokunin`, not the typographical spelling). The run returned **130/130 results**, each with separately captured process return code, stdout, and stderr; all 130 stderr values were empty. There are 130 fixture directories and **645 JSON files** in the fixture tree. The replay is the active checker at the declared baseline, not archived-old-checker versus candidate evidence. A future implementation must not treat this baseline run as proof of regression preservation.

Raw tuple effects relevant to this proposal:

- Exactly one current fixture emits `claim_a and claim_b references must differ`: `.shokunin/lore/corpus/fixtures/r62-malformed-side/`. Its `contradictions.json` has both event IDs equal to `tarin-envelope-observation` and both fields equal to unsupported `bogus`; `timeline.json` is malformed. Current CLI returns 1, stderr empty, and emits (in order) the timeline load error, one invalid-field error for each side, the same-reference error, and `4 violation(s); no canon changed`. Thus the duplicate-reference finding is currently additive to two side-local field errors even though `bogus` is not an allowed assertion field and the event index cannot load. This is the direct exposed tuple under the Round 69 claim.
- The ordinary valid unique-pointer control `.shokunin/lore/corpus/fixtures/r37-ledger-unique/` is clean (exit 0; `CLEAN: schema, citations, relations, timeline; 0 violations`). Its two ledger endpoints use distinct valid event/field pairs.
- `.shokunin/lore/corpus/fixtures/r37-ledger-ambiguous/` has a duplicate timeline event ID and emits the duplicate-ID finding plus `claim_a.event_id: expected exactly one timeline event ...` (exit 1, 2 findings). It does not contain an identical-side reference, so it does not directly test the proposed gate.
- `.shokunin/lore/corpus/fixtures/contradictions-ledger-malformed/` contains a valid distinct pair for its first ledger record and a second record with distinct references (`arrival/depends_on`, `absent-event/tick`); output includes the absent timeline ID and three other findings, with no same-reference finding.
- `.shokunin/lore/corpus/fixtures/r62-malformed-side/` is not a matched control pair. No four-case Round 69 control matrix exists in the fixture tree as inspected. In particular, I found no committed case for malformed-one-side with equal event but different fields; valid-identical allowed pairs; or valid-different pairs deliberately arranged with one or both timeline targets unresolved. The current fixture set cannot establish the full promised calibration boundary by itself.

The source check matters: in `check_bible.py`, each side continues on invalid `event_id`/field, unavailable timeline, or non-unique event before the final equality test, but there is no flag recording whether both side references passed those checks. The final test therefore can add a same-reference error after malformed-side findings. For this proposal, “valid” should mean the declared well-formed pair criteria in `.shokunin/lore/LOG.md`: nonempty string event ID and allowed field; do not silently narrow the test to successfully resolvable event IDs unless the declaration is explicitly revised. The checker currently permits the same-reference test even when those syntactically valid IDs cannot resolve; the requested controls need to make this scope explicit.

## Pinned replay plan for any candidate

Before candidate evaluation, independently archive baseline `583f97e40f0c5d0bcd0c51be1a408e7d3005b9c6` (or provide equivalent immutable byte evidence) and derive the old fixture-directory and corpus-path manifests from that archive. Do not rely only on present working-tree counts. Record the exact checker SHA-256 and hashes/raw bytes for all 645 baseline fixture JSON paths; include the checker, README, any non-JSON fixture inputs, and full path additions/removals in the corpus manifest.

Run the archived baseline checker and candidate checker against each exact archived fixture directory. Use identical repository-root cwd and repository-relative argv for both; capture **raw stdout bytes, raw stderr bytes, and exit status separately** for each of the 130 baseline cases. Compare tuples byte-for-byte, enumerate every changed case and its precise lines/count/status; do not normalize path-bearing errors or compare only exit/pass status. Candidate must not change existing fixtures to make replay green. Also compare all original corpus path bytes, explicitly listing expected and unexpected changes. This yields the old-corpus delta; it does not substitute for new discriminating cases.

Add temporary or committed matched controls, with all irrelevant tables byte-identical and stdout/stderr/exit captured for both checkers:

1. Two syntactically valid, allowed, identical `(event_id, field)` pairs; test a unique event target and, separately if the intended gate is structural rather than resolvability-based, an unresolved but syntactically valid event ID.
2. Identical nonempty event IDs with different allowed fields, to show same event alone is not duplicate reference.
3. Malformed `field` values equal on both sides (the existing `r62-malformed-side` case is a starting point) and malformed-one-side / independently malformed-side variants; verify each side's own diagnostics survive and the same-reference finding is removed only where the declaration says both references are invalid.
4. Malformed or empty event IDs, equal and unequal counterpart values, and valid-side/invalid-side combinations; ensure the proposed condition is specifically both sides structurally valid and does not suppress a legitimate valid-identical finding.
5. A valid identical reference pair whose IDs resolve uniquely, and a valid different-reference pair, as positive/negative guard controls. Keep all unrelated source, entity, relation, and timeline inputs fixed and valid; also retain a separate unrelated-error control if needed to prove errors are not lost.

Check output order and totals as well as diagnostic presence. The intended behavior is removal of the redundant/unsupported equality finding only for invalid equal pairs, while both local malformed-field diagnostics and valid-identical-reference detection remain. If candidate changes any of the other 129 established tuples or changes an allowed valid-identical tuple, record and assess it as a regression rather than assuming harmlessness. Candidate and controls should be evaluated on the pinned checker, not an evolving worktree.

## Limits

This scout did not create candidate fixtures, archive and replay an independent baseline checker, or assess the materiality of an implementation. The baseline 130-result run only describes the active declared-HEAD checker on present inputs. No fixture raw result establishes source meaning, authored intent, truth, in-world contradiction, canon, rights, permission, or game mechanics. The scope is strictly diagnostics over supplied JSON structure and the checker's ledger-reference predicate. No checker, fixture, README, LOG, or other report was changed; this report is the sole intended write.
