# Round 60 prior-scout — unavailable-table cascade and certainty precedent

## Calibration decision: NO-GO on this prior-only evidence

**Observed:** the r59 checker converts every load failure to an empty list, so downstream consumers cannot distinguish “loaded, no rows” from “unavailable.” `check_bible.py:38-51` catches duplicate-member and read/JSON errors, sets `rows = []`, then records `data[section] = []`. In the nested duplicate fixture this causes six relation/timeline `dangling entity` diagnostics after `entities.json` fails (`LOG.md:1018, 1027`; r59 nested fixture/report). These are consequences of the representation, not evidence that entities are absent. R59 deliberately admitted and documented this cost (`LOG.md:1027-28`), leaving suppression for a fresh round (`:1031`).

**Prior-art boundary:** r5 measured a missing `contradictions.json` and other isolated malformed inputs with one primary error in its selected low-cascade cases (`LOG.md:60-68`). It does not establish behavior for an unavailable, heavily referenced entity/source/event table. R5 explicitly bounded its observations; extrapolating its low-cascade result would be unsound. R59’s nested fixture is direct observed high-cascade evidence, but only for entities and this duplicate-member failure mode. No paired unavailable-vs-loaded-empty control or complete cross-table status policy was found in the cited record.

**Relevant certainty policy (r11–19):** the checker’s established pattern is narrow suppression of a conclusion dependent on unresolved or invalid reference data while retaining the input finding and independent checks. R11 counts screened entity rows for `timeline.place_id` and withholds kind selection only when ambiguous (`LOG.md:152-64`). R12 withholds definite same-actor occupancy under multiple screened entity matches, explicitly not asserting there is no real conflict (`:167-78`). R13 gates occupancy on exactly one screened actor row, preserving dangling findings and raw events (`:180-92`). R17–18 require uniquely resolved, correctly-kind place references and preserve ambiguity diagnostics (`:244-74`). R19 excludes invalid negative ticks from occupancy while retaining other dependency processing (`:276-88`). These precedents support saying “not assessable” rather than “false/absent” when a lookup is unresolved; they do **not** establish a general unloaded-table rule. The existing table-wide `[]` fallback is notably unlike those field-local count guards.

## Observed behavior vs proposed rule

Observed at `check_bible.py:127-50, 248-94`: entity claims, relation endpoints, timeline actor/place checks and provenance holders consult the entity index; `source()` treats a zero source count as `unknown` (`:84-94`); event dependencies consult timeline IDs (`:273-94`). When a table fails to load, its index/counts appear empty. A hypothetical suppression should apply only to conclusions whose lookup depends on that unavailable table, retaining the load diagnostic and checks using other loaded data. It must not call the missing table “empty,” silently choose a duplicate JSON value, or suppress independent schema/dependency checks. This is a proposal, not implemented or replayed. The current cascade is structurally analogous across entity/source/timeline references, but only entity cascade is observed in r59; equivalent cases are not evidence yet.

## Falsifier / reversal condition

Reverse this NO-GO if paired, independently replayed inputs show a stable, consequential false “unknown/dangling” conclusion solely from a required table being unavailable, while a successfully loaded empty/partial table correctly retains those findings; then define table-specific dependent checks and demonstrate suppression does not hide independent findings. Include duplicate-member, missing-file, invalid-JSON, and wrong-shape load failures, and preserve low-cascade r5 outputs where unrelated. A supported contract that treats failed tables as empty would falsify the proposed uncertainty distinction. Conversely, a rule that suppresses findings for a successfully loaded empty table is a regression, not calibration.

## Cascade / regression risk

Changing `[]` to an unavailable status may affect more than six entity references: source lookups can stop reporting unknown IDs, timeline event indices can affect contradiction references/dependencies, and provenance/relations/timeline have separate checks. Broadly skipping a loop risks hiding independent diagnostics; per-check gating risks inconsistent semantics. The six r59 findings are a concrete bounded cascade, not six independent malformed facts. Keep unavailable distinct from loaded-empty; preserve file-level error and raw input; account for all old 99 CLI tuples/494 old JSON bytes and enumerate intentional r59 deltas before admitting any change. No table failure establishes world absence, fictional entity nonexistence, source-text/canon truth, or rights/permission.
