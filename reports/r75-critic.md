# Round 75 critic — attempt to defeat exact relation-duplicate coverage claim

## Scope and evidence

I read the Round 75 declaration in `.shokunin/lore/LOG.md`, active `corpus/fixtures/check_bible.py`, `corpus/fixtures/README.md`, and relevant predecessor reports: `r2-rule-scout.md`, `r2-critic.md`, `r2-axis-adjudicator.md`, `r7-critic.md`, `r8-critic.md`, `r8-axis-adjudicator.md`, `r9-axis-adjudicator.md`, and `r45-axis-adjudicator.md`. The declared baseline is `58edd17eb080fc707e959bf3dfc56d01afa54234`. This report addresses the proposed rule/materiality, not an implementation: no r75 checker or matched r75 fixtures were present in the inspected tree. I did not edit corpus, LOG, or checker files.

The relation row schema is exactly four required strings: `from`, `to`, `type`, `source_id`. The checker checks endpoints and source-ID membership, then applies a narrow reciprocal convention to distinct faction `allied_with` pairs. It does not enforce relation-row uniqueness. The README requires citations and says source IDs point to in-world fictional records; it does not define whether relation rows are a set, a multiset, a claim per passage, or a normalized representation. The relation checker never reads source prose or counts mentions. `source_id` therefore cannot distinguish two mentions in a record from a duplicate serialization of one assertion.

## Strongest materiality counterexample

Suppose one fictional source has two separate passages that each state the same directed relation. Because the schema has no passage/claim identifier, a data author might encode that same `(from, to, type, source_id)` tuple twice to preserve two source mentions. The proposed exact-tuple warning would label the second row an input duplicate even though, under this plausible representation, it is a second occurrence. It cannot tell the author which interpretation applies, and it cannot safely repair the data by deleting either row. A warning is not itself proof of harmless normalization: deleting it may discard a mention, while retaining it may double-count a relation in any consumer. This is the same-source multiplicity the LOG itself leaves open, not a demonstrated canon-level duplicate.

The opposite case is equally plausible: if rows are meant to be unique relation assertions and a citation is only a record-level pointer, the second tuple is redundant encoding and a row-indexed warning is actionable. But that uniqueness contract is not in the observed schema or README. A matched duplicate-vs-distinct-source-vs-reverse-edge fixture can demonstrate that code distinguishes exact tuples and leaves controls alone; it cannot establish which data model is correct or that the warning is materially useful rather than a newly invented convention. The only existing relation in `consistent/` is one `mira -> seal / carries` row, so it provides no repeated-mention precedent. The LOG's inventory of 132 fixtures likewise says none has an exact repeated tuple; absence of a counterexample in that inventory is not evidence for a uniqueness contract.

## Redundancy and calibration risks

- Existing reciprocal behavior is about presence of a reversed faction alliance row, not uniqueness. Repeating a forward edge does not satisfy the reverse edge; if a reverse edge exists, extra forward copies do not alter that test's result. A duplicate diagnostic would be a separate policy, not a missing reciprocal check.
- Existing endpoint and citation checks already report invalid endpoints or unknown/ambiguous source IDs on each relation row. With a repeated invalid row, the new warning could add a third structural complaint alongside per-row findings. That may be useful, but needs a declared diagnostic policy and evidence the added report is actionable, not merely more output.
- Same `source_id` is not the same source passage; different source IDs are not necessarily independent testimony. A duplicate warning must not be worded as duplicate evidence, corroboration, source repetition, or proof that the relation was asserted only once.
- The r8 precedent admitted repeated dependency IDs as a narrow **input-list-integrity** rule after identifying dependency entries as set-like, isolating an earlier prerequisite whose repeated token previously passed, and defining cascade behavior. That precedent does not establish that relation rows are set-like. R2's rule scout explicitly says duplicate-relation policy is undeclared and cautions not to add it under the reciprocity move.
- No repair is safe on the evidence available. An advisory finding can prompt review, but cannot decide whether to remove a row, merge mentions, or alter either cited assertion. Calling it a useful “duplicate” diagnostic presupposes the policy under dispute.

## Verdict

**NO-GO on admitting material coverage improvement on the current declaration/evidence.** The checker lacks an exact-tuple detector, so a structural difference is implementable; however, demonstrating that detector on a synthetic pair only proves a predicate was added. The intended schema meaning of repeated rows is unresolved, and the plausible multiple-mention case defeats the claim that every exact repeated tuple is actionable duplicate input. No delivered fixture or source-text evidence settles that ambiguity. At most, a future round could propose an explicitly named *authoring convention* (“relation tuples must be unique”), document that it may flag repeated mentions encoded as repeated rows, and validate that convention with the project owner; it should not describe the result as source-truth/canon validation. This round should not claim coverage until that contract is established.

**Axis assessment for this proposal:** coverage **not demonstrated / NO-GO**; depth **unchanged** (no richer source or lore semantics); calibration **at risk, not proven harmed** if a bare warning calls records duplicates or invites deletion. Structural duplicate, source truth, canon, rights, and mechanics are separate: this proposal can test only equality of four input fields. It cannot determine whether prose repeats the relation, whether a citation supports it, whether sources are independent, whether the relation is canonical, or any rights/game-mechanics issue.

## Limits and falsifiers

This is a schema/policy critique, not proof that repeated tuples are legitimate in the intended data model. I did not run hypothetical temporary fixtures, inspect source passages for repetition, or verify the declared 132-fixture baseline replay. Those tasks cannot resolve the missing uniqueness contract by themselves. The NO-GO would be falsified by an explicit authoritative schema/editorial rule that relation rows are unique by `(from,to,type,source_id)` and should be checked; then a narrowly worded, non-repairing warning with a distinct-source and reverse-edge control could be assessed for coverage, and old raw CLI tuple replay would test regression preservation. Even then, the checker must continue to say this is input structure only, not source truth, canon, rights, or mechanics.
