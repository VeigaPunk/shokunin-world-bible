# Round 3 critic — falsification attempt

## Evidence at inspection

The Round 3 claim is recorded in `.shokunin/lore/LOG.md` (“Round 3 — 2026-10-12 (depth axis-move; declaration before dispatch)”). At this snapshot, the claim is **not demonstrated**: `.shokunin/lore/corpus/fixtures/check_bible.py` has `FIELDS` only for `sources`, `entities`, `relations`, and `timeline`, and contains no contradiction-ledger loader or validator. The `contradictions/` fixture contains only those four JSON files; its `entities.json` claim objects have `statement` and `source_id`, but no claim IDs. A fresh run of `python3 .shokunin/lore/corpus/fixtures/check_bible.py .shokunin/lore/corpus/fixtures/contradictions` exits 1 with the three original violations (dangling `missing-map`, inversion `arrival` → `later`, and double booking `arrival`/`false-sighting`). This verifies baseline behavior only, not the promised ledger behavior; implementation may still be in flight.

## Falsification risks (scenarios, not observed failures)

1. **A syntactically valid reference can be a phantom or point at the wrong assertion.** No current entity claim has an ID (`.shokunin/lore/corpus/fixtures/contradictions/entities.json`), and there is no established reference grammar. A validator that accepts an arbitrary string, checks only that a source ID exists, or resolves a non-unique locator could accept references that identify no assertion or identify the wrong one. A timeline event ID is more stable (`timeline.json`: `arrival`, `false-sighting`, `later`), but resolving an event row does not by itself identify which field is asserted. For example, `arrival` has a cited `description`, `tick`, `place_id`, and `depends_on`; a broad event reference could ambiguously stand for any of them.

2. **The existing seeded violations are not all pairs of sourced claims.** The timeline disagreement has two rows with distinct source IDs: `arrival` and `false-sighting` in `contradictions/timeline.json` cite `courier-log` and `archive-ledger`; both IDs exist in `contradictions/sources.json`. But `arrival.depends_on: ["later"]` is a structural field in the fixture, not a separately identified/source-cited assertion; `later` has a row-level source, which does not establish that the source supports the dependency declaration. The dangling `relations.json` entry `mira -> missing-map` has no second record at all: `contradictions/entities.json` has no `missing-map`, and `sources.json` supplies no source for a denial. The round-3 claim says “each record” has two resolvable cited claims, not that every checker violation must get a ledger row; nevertheless, a ledger presented as covering all three seeded conflicts would need to invent a side for `missing-map` or weaken “resolvable cited claims.” Do not infer coverage from preserving three diagnostics.

3. **Nonempty `why` is arbitrary free text, not a verified explanation.** A check for string/nonempty accepts unrelated text, a restatement that one side is true, or a claimed conflict between compatible assertions. The checker has no semantic contradiction test, and the LOG expressly calls ledger references editorial rather than semantic proof. Therefore a green ledger check can establish only shape/reference resolution, not that `why` accurately explains an incompatibility or that the two claims contradict. This is a limit on the claim's evidential force, not necessarily a defect if “why” is explicitly treated as unchecked editorial text.

4. **Source identity can be mismatched while IDs resolve.** Existing validation resolves `source_id` against `sources.json`; it does not inspect source contents or determine whether a source supports the cited statement (`check_bible.py` `source()` and claim checks; `fixtures/README.md` says citation is not proof of truth). If ledger entries copy `statement` or `source_id`, a mismatch with the target row could create a phantom cited claim even when both source IDs exist. If the reference points to a row instead, row-level sources (`arrival` → `courier-log`, `false-sighting` → `archive-ledger`) are traceable but still do not prove textual support or source agreement. Two ledger sides that reuse one citation, or cite the wrong existing source, can pass mere existence checks.

## Recommendations (not existing behavior)

- Specify one exact reference representation and resolve it to exactly one existing assertion; reject missing, duplicate, wrong-section, and ambiguous targets. If references carry copied text/source IDs, compare them exactly with the target rather than accepting independently valid but mismatched values. A stable claim ID or explicit record-and-field locator is safer than free-form prose.
- Keep source validation separate from support/truth claims. Require each referenced assertion to inherit or resolve its own actual citation; do not let `why` or the other side's citation substitute for it. Describe successful validation as structural pointer/citation checks only.
- State that `why` is unchecked editorial annotation unless a separate review validates it. Do not describe nonempty-text validation as validating the reason or contradiction.
- Either leave the dangling `missing-map` diagnostic outside the two-sided ledger, or explicitly report that no second cited assertion exists. Do not manufacture an entity, source, or denial to satisfy the ledger shape.
- For falsifiable evidence, retain the original three checker outputs and test both valid and malformed reference/source-mismatch cases. A valid and malformed pair alone should not be described as proving semantic contradiction or exhaustive coverage.

## Conclusion

At this inspection point, the round-3 claim remains unproven because no ledger implementation or fixture is present in the observed tree. The most important boundary is that “resolvable cited claims + nonempty `why`” can at best establish well-formed editorial pointers and existing source IDs; it cannot establish that the citations support the precise assertions or that the free-text reason is correct. The dangling-endpoint seed is a concrete limit on representing all existing violations as pairs. These are findings and recommendations for the stated claim, not assertions that a later implementation failed.
