# Round 6 critic: immediate-prior-holder rule

## Observed repository evidence

- The active checker has no provenance table: `.shokunin/lore/corpus/fixtures/check_bible.py:8-15` declares exactly five tables, and its timeline rows have event IDs/ticks but no item/holder fields (`:12-13`). Existing `consistent/entities.json` contains `seal`, a cited claim that it accompanied Mira; `relations.json` records Mira `carries` the seal, both citing `courier-log`. Neither says when Mira acquired it or who held it before her. `sources.json` says the courier log is a first-person account, not omniscient truth.
- The checker’s `index()` reports duplicate IDs but then overwrites the prior mapping (`check_bible.py:45-51`). Entity duplicate counts are later used to suppress the alliance rule (`:111-122`); timeline IDs get explicit counts only for contradiction references (`:57-60`, `:76-86`). Any new provenance logic that follows the simple index pattern can accidentally derive a holder from whichever duplicate row was processed last.
- Timeline inversion currently means a dependency event tick must be strictly less than the dependent event tick (`:151-155`). Same-tick transfer records therefore have no defined relative order under the existing timeline convention. Timeline event records also describe places/events, not item possession; their event IDs should not be silently treated as provenance records.
- Contradictions are explicit cited references to timeline event fields (`:65-91`); the checker validates pointers and source resolvability but does not adjudicate conflicting claims. Source resolution only checks that an ID exists (`:61-63`); reliability notes are not used to rank or reconcile sources.

## Falsification cases / gaps

1. **No baseline holder:** the current clean `seal` data says it accompanied Mira / Mira carries it, but provides no acquisition or earlier holder. Treating the first transfer’s `from_holder` as the “immediately prior holder” merely repeats that row’s assertion; it cannot establish the prior holder from an acquisition/previous transfer as the LOG claim requires. Conversely, requiring a seed acquisition would reject a transfer-only record set unless that seed is supplied. Do not infer the seed from `first_appearance`, claim text, or the `carries` relation: none encodes an acquisition time or predecessor.
2. **Same tick:** two transfers for one item at the same tick (A→B and B→C) can be valid in either row order, while A→B and C→D are incompatible. Sorting only by tick leaves the result dependent on input order, and the existing strict timeline ordering does not resolve equal ticks. A local diagnostic needs a stated tie policy (e.g. reject ambiguous same-item same-tick records, or introduce an explicit sequence/order key); otherwise the “immediately prior” result is not stable.
3. **Disputed source assertions:** two individually resolvable sources may assert different prior holders at the same time. Current source validation proves only ID existence, and contradiction handling is an editorial ledger, not an answer selector. A chain break between rows may flag a mismatch but cannot identify which source is right. Preserve both claims and report the local conflict; never choose a winner based on source order/reliability text.
4. **Timeline mismatch:** a transfer tick can disagree with a cited timeline event’s tick, and no existing schema links a transfer to a timeline event. If the feature intends transfer ticks to be timeline ticks, require an explicit uniquely identified event reference and compare ticks; otherwise define transfer tick as its own local sequence and do not claim synchronization with the timeline. Same-tick ambiguity remains either way absent an ordering key.
5. **Duplicate IDs / ambiguous endpoints:** entity IDs are not safe chain keys when duplicated: `index('entities')` keeps the last row after reporting a duplicate. A duplicated item ID could resolve to an item or non-item depending on order, and a duplicated holder ID can designate multiple entities. Existing timeline ID counting shows the repository already treats duplicate timeline IDs as unsuitable for unique references. Provenance should skip/avoid deriving chains for non-unique item/holder IDs and report ambiguity, not emit a misleading predecessor verdict. If transfer records themselves receive IDs, enforce uniqueness too.

## Recommendation (not implemented)

Do not admit the “first transfer from A proves A was the prior holder” interpretation as satisfying the declared claim. Either (a) require an explicit cited acquisition/initial-holder record to seed a chain, then check subsequent transfers, or (b) narrow the claim to continuity among transfers and label the first transfer’s predecessor as an unverified source assertion. In either design, make ordering deterministic (strictly increasing per-item ticks or explicit sequence), surface disputed assertions without resolution, specify whether ticks share the timeline, and suppress chain judgments for duplicate/ambiguous entity IDs. Keep the transfer table optional so absence is not a failure. These are recommendations, not observed implementation or canon facts.
