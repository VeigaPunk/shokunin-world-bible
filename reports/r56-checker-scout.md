# Round 56 checker scout — provenance holder ambiguity

## Independent calibration judgment

**GO, narrowly, for a holder-reference-local ambiguity diagnostic as a proposed checker calibration move; this is not implemented.** The checker silently gates provenance-chain comparison when a holder ID is nonunique. A local finding at the precise `to_holder` / `from_holder` path would tell a reader which asserted holder reference cannot resolve uniquely, while retaining (not resolving) the record and the existing global duplicate-ID finding. This is a modest practical diagnostic improvement, not new semantic coverage, not proof the global duplicate is inadequate for every operator, and not a basis to infer actual custody or canon.

## Prior-art calibration / limits

Round 6 (`reports/r6-critic.md`, `r6-scribe.md`, `r6-provenance-scout.md`) warns that holder-chain assertions must not be inferred from prose, a `carries` relation, or `first_appearance`, and duplicate IDs must not drive chain judgments. Round 11 (`reports/r11-scribe.md`) documents that duplicate IDs plus last-row indexes can make reference interpretation order-sensitive; it deliberately discusses place/actor scope, not holder references. Rounds 24–27 establish a useful checker precedent: emit local ambiguity at each affected relation endpoint, retain global duplicate finding, never choose a duplicate. Round 26 specifically distinguishes schema-admitted duplicates from malformed rows excluded by required-field screening. These precedents support an analogous local diagnostic, but do not establish its materiality by themselves.

## Proposed bounded behavior (not observed/implemented)

For provenance holder fields, use multiplicity among schema-admitted entity rows: count 0 keeps the existing dangling diagnostic; count 1 keeps current behavior; count >1 keeps the global duplicate and adds a field-local `ambiguous entity <id>` diagnostic, one per affected `to_holder` or non-null `from_holder`. Do not choose/merge a duplicate or compare holder chains through that ambiguous reference; retain the existing chain-gating behavior. `from_holder: null` remains a null acquisition marker, not a reference. Malformed duplicate rows excluded by schema screening must not trigger ambiguity. Preserve the raw records and all source diagnostics. If exact diagnostic wording differs, it must still be explicit that ambiguity is fixture-ID multiplicity, not real-world identity.

## Falsifier and anticipated collateral

**Falsifier:** In a matched schema-valid duplicate-holder input, reviewers show that the global `entities[i].id: duplicate ...` finding already reliably identifies every affected provenance reference without ambiguity about scope, while local findings add no useful pinpointing (or materially obscure the primary result). Then this is redundant/no-go; do not count row count as coverage. Also reject if a candidate emits local ambiguity for malformed/excluded duplicates, chooses a duplicate, or permits chain comparison across an unresolved holder.

**Collateral:** Additional violation lines and changed raw output/exit-summary counts for any existing corpus case with duplicate IDs used by a provenance holder; possible noisy repeats when one duplicate holder occurs in many records, and downstream exact-output snapshots must be reviewed. The new text must not imply theft, removal, actual custody, holder identity, source truth, completeness, rights, permission, or canon. Depth and coverage stay unchanged; the only claimed axis is calibration. No old raw outputs or corpus files were changed by this scout.
