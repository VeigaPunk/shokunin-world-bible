# Round 44 ontology scout: timeline actor kind

## Finding

**No-go on an unconditional character-only actor rule.** The schema and checker treat `timeline.entity_id` as a generic entity reference; the repository's current fixtures happen to use characters for resolved timeline actors, and the README gives a character-specific occupancy convention, but those facts do not establish that every timeline event's subject must be a character. Treat the proposed premise as unproven, not as an existing invariant. Do not implement the proposed rejection of a place actor on this evidence.

## Evidence (path:line)

- `.shokunin/lore/corpus/fixtures/check_bible.py:7-14`: entity kinds are `character`, `place`, `faction`, `item`; timeline required fields declare only `entity_id: str` (no kind constraint or actor-specific schema).
- `.shokunin/lore/corpus/fixtures/check_bible.py:229-252`: timeline processing checks that both `entity_id` and `place_id` resolve to entities, reports ambiguous actors, and uses a uniquely identified actor ID as an occupancy key. Unlike the `place_id` branch at lines 237-241, it never checks the resolved actor entity's kind. The occupancy rule only uses the ID/tick/place certainty conditions at 245-252.
- `.shokunin/lore/corpus/fixtures/README.md:29-34`: documentation defines a local tick and says “A character cannot occupy different places at the same tick.” This is a specific occupancy assertion, not a declaration that all timeline `entity_id`s are characters or that non-character subjects are invalid. The nearby source-citation rule at 36-40 likewise says event, not character-event.
- Inventory checked across every `corpus/fixtures/*/timeline.json`: 226 actor occurrences resolve to `character`; the only unresolved actor occurrences are the two deliberately dangling `unlisted` IDs in `r13-missing-actor`. No current resolved non-character actor example demonstrates intended acceptance, but absence is not a schema rule.
- `.shokunin/lore/LOG.md:157-164` (r11) scopes its kind rule explicitly to `timeline[i].place_id`; line 158 expressly leaves “timeline actor identity” outside that round. This is a boundary statement, not an actor-kind convention.
- `.shokunin/lore/LOG.md:167-178` (r12) concerns duplicate actor-ID ambiguity and occupancy attribution. It distinguishes ambiguous identity from a definite same-actor comparison; it does not constrain the unique actor's kind.
- `.shokunin/lore/LOG.md:308-320` (r21) tests malformed dependency lists masking occupancy, preserving a character actor (`mira`) in both controls. It establishes no non-character actor policy.
- `.shokunin/lore/fixtures` does not exist; the r11/r12/r21 fixture evidence is in `.shokunin/lore/corpus/fixtures/` as cited below. `r11-place-character/timeline.json` and `r11-character-place/timeline.json` (each first event has `entity_id: mira`, `place_id: harbor`) test place-reference row-order ambiguity, not actor-kind acceptance. `r12-unique-actor/timeline.json` uses `mira` for both actors; `r12-ambiguous-actor/timeline.json` adds a duplicate `mira` entity row. `r21-clean/timeline.json` and `r21-malformed/timeline.json` both use `mira`; only `depends_on` differs (`[]` vs `[null]`).

## Risk / interpretation

The evidence supports a distinction between *current data convention* and *schema guarantee*: authored examples consistently choose character actors, but the field is expressly a string entity ID and checker treatment is generic. A place, faction, or item could be the subject of an event (for example, a location's opening/closure, a faction's treaty, an item's transfer) without violating any declared `timeline` field rule. Whether those meanings belong in this particular event model is a domain policy question not answered by the cited examples. Hard-rejecting them would therefore codify a new ontology decision, potentially excluding legitimate event subjects and misrepresenting the existing checker contract. Conversely, the generic field does not prove all such subjects should be accepted; no resolved non-character actor fixture tests it.

The README's character occupancy sentence can support a narrowly stated rule about character occupancy if the project explicitly decides that `entity_id` denotes a character for that class of events. It does not justify applying the rule to all timeline rows. Citation-ID resolution is not source-text evidence that a given subject acted, and fixture identifiers/descriptions do not establish canon.

## Falsifiable next step / gate

**Current candidate: NO-GO for an unconditional character-only kind check.** Before any checker change, obtain an explicit ontology decision that answers whether `entity_id` is always a character or whether event subjects may be any entity kind, and defines how the existing character-only occupancy check applies to non-character subjects. Then add a controlled, uniquely identified non-character actor case (at minimum place; preferably one per intended allowed kind) with a documented event meaning and a character control. A falsifiable policy test must show either: (a) under an explicit character-only rule, the non-character case gets exactly a field-local kind diagnostic while the character control stays clean; or (b) under a generic-subject rule, a legitimate non-character event passes structural validation and does not participate in character-occupancy inference. Recheck all prior fixture outputs. If no policy and no such fixture exist, retain the current generic schema and do not implement the proposed guard.
