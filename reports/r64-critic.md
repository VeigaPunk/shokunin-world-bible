# Round 64 critic — malformed entity ID as membership witness

## Independent calibration verdict

**NO-GO on the declared material benefit, pending actual paired probes.** The proposed distinction is conceptually plausible: a successfully parsed array can contain a row with `id: "mira"` that fails another required-field check, so retained valid-row counts say zero even though the raw input mentions that ID. But the current checker already preserves a row-local schema error, and the declaration itself acknowledges that treating the raw ID as a membership witness may hide the useful `dangling entity` repair pointer. That tradeoff is not demonstrated to be a material calibration gain by this critic. No r64 temp probes or proposal outputs were observed here; only current-code behavior is described below.

## Current behavior (observed by inspection)

- `.shokunin/lore/corpus/fixtures/check_bible.py:64-76` appends a row to `data[section]` only when it is a dict and passes every required field check. A bad row therefore produces its field-local schema message, but is excluded from all later indexes.
- `:78-95` constructs indexes/counts only from admitted rows. The `entities` index and `entity_id_counts` at `:90` and `:156-159` therefore do not treat an invalid row's ID as present or unique.
- `:161-168` reports absent relation endpoints as `dangling entity`; `:269-284` similarly reports missing timeline actor/place references and uses only admitted rows to decide ambiguous/not-a-place status. The provenance logic at `:203-224` independently reports malformed holder shape and otherwise zero-count holders as dangling; a non-unique count gates its chain at `:234-237`.
- This means the proposed raw-ID suppression could remove a dangling finding while retaining only a generic schema field error elsewhere. It would not establish a valid entity, identity, kind, holder, place, faction, or occupancy witness. The question is whether a location-specific “cannot assess: matching row invalid” adds enough useful localization to justify taking away the current explicit pointer; no such result was observed.

## Materiality and repair-pointer harms

A malformed row's string is merely an ID token in supplied JSON, not evidence of an entity in the fictional world. Conversely, a `dangling entity 'mira'` currently points the operator directly from each affected reference to the unresolved table membership; it can prompt correction of a typo in either the reference or entity row. Suppressing it on a raw string match may obscure a real typo/near-match, especially where the malformed row ID differs subtly from the referenced token, or where another schema defect makes the row unusable. It may also mask a separate missing valid row when a malformed duplicate happens to share the ID. The row-local schema error may be far from, or fail to explain, each downstream reference.

A narrowly scoped “matching entity row invalid” status could be more calibrated than a definite dangling only if it is tied to the exact same nonempty ID, is emitted at each dependent reference, preserves the original schema error and all independent checks, and does not allow the row to qualify for any positive check. Even then it trades a concrete repair pointer for uncertainty; the operator may need both messages rather than replacement. The declaration's alternative of retaining the dangling pointer while additionally identifying an invalid match deserves comparison before claiming benefit.

The calibration claim is falsified if the proposal suppresses an absent/near-match reference, lets any malformed row satisfy a uniqueness/kind/holder/place/faction/occupancy condition, hides independent source/tick/dependency findings, or emits no more actionable reference-local information than the retained row schema error plus current dangling pointer.
